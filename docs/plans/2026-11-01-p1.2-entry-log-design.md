# P1.2 Entry Log Recording — Design Spec (DRAFT)

**Status:** unfinished. Section 1 approved by the owner on 2026-11-01 (session 13); section 2 presented, the owner's answer is still open; section 3 not yet presented. No implementation plan until the whole spec is approved.
**Task:** P1.2 in `docs/PROGRESS.md`. **Related ADRs:** 0007 (rule 2: append-only; rule 3: one transaction per action), 0019 (default privileges), 0027 (tenancy). New ADR: 0028 (entry-log table shape).
**Requirements used:** `00` #20 (every action is recorded against the logged-in person), `01` #11 (stock adjustments carry a reason), Module 06 (still DRAFT: only the recording side is built here; the viewer and the unusual-activity flags wait for `/finalize-module 06`).

## 1. Goal and what the owner confirmed

From the first feature that changes data, every change gets one permanent log row: who, what, when, old value → new value. The viewer is P2.6. Recording comes first, or the early history is missing.

Owner's answers and assumptions (2026-11-01):
- **Who:** `actor_id` is a nullable UUID with **no foreign key yet** (option A). NULL means the system (e.g. the worker). P1.4 adds the users table and a migration adds the composite key. Rejected: a minimal `users` table now (pulls P1.4 in), a free-text name (weak evidence).
- **Old → new:** two `jsonb` columns, `before` and `after` (option 1). Rejected: one row per changed field (a 20-line bill becomes a pile), a single `{field: [old, new]}` (every module would compute the diff, and a mistake would corrupt history silently).
- **Retention:** rows are kept forever (assumption; revisit at `/finalize-module 06`).
- **Module 06 stays DRAFT.** Only recording is built.

## 2. The table `entry_log` (approved)

| Column | Notes |
| --- | --- |
| `id` | UUIDv7 via `id()` |
| `business_id` | `businessId()` helper; default `app_current_business_id()`, so the helper never passes it and can't write to another business |
| `branch_id` | optional; composite key `(business_id, branch_id) → branches(business_id, id)` (the guard demands it) |
| `actor_id` | uuid, nullable, no foreign key yet; NULL = the system |
| `action` | text such as `stock.adjusted`; not a database enum, because a new action would need a migration. The allowed names are a TypeScript type, so a typo fails type-checking |
| `entity_type`, `entity_id` | what was changed |
| `reason` | text, optional |
| `before`, `after` | jsonb, optional |
| `created_at` | `createdAt()`, set by the database |

- Standard tenant table: `tenantPolicy(t.businessId)`, `ENABLE` + hand-written `FORCE ROW LEVEL SECURITY` in the migration.
- **Append-only:** the migration runs `REVOKE UPDATE ON entry_log FROM app_runtime`. DELETE and TRUNCATE are already missing from the default privileges (P0.3).
- No `SECURITY DEFINER` function, so PUBLIC's default EXECUTE is not an issue here.
- `app_owner` owns the table and could still update it. It is the migration role and never runs at runtime (ADR 0007 restricts only the runtime role).

## 3. The write helper `recordEntry` (presented, awaiting the owner's OK)

In `packages/db/src/entry-log.ts`:

```ts
await withBusiness(db, businessId, async (tx) => {
  // ...the business action itself...
  await recordEntry(tx, {
    actorId, // string | null, required (null = the system)
    action: 'stock.adjusted',
    entityType: 'item',
    entityId: itemId,
    reason: 'Damaged in transit',
    before: { quantity: 10 },
    after: { quantity: 8 },
  });
});
```

- Takes a `Transaction`, not the database: it can't be called on its own, so the log row and the action commit or roll back together (ADR 0007 rule 3).
- `actorId` is required but may be `null`: forgetting "who" is a type error; "the system" has to be written on purpose.
- Actions are a typed list in code, starting with what is decided (`stock.adjusted`). Each later module adds its names. The list also says which actions need a reason (`stock.adjusted` does); the helper rejects a missing or blank reason before touching the database.
- `before`/`after` are plain JSON; money inside is integer paise. A value that can't become JSON throws.
- It only writes. No read function (the viewer is P2.6); tests read the table directly.
- With no business set, `business_id` is NULL and the insert is refused.
- Open detail: whether `packages/db` may import the action list from `packages/shared` (check the package dependencies; if not, define the list in `packages/db` or add the dependency).

**Tests:**
- a recorded row has the right fields, and `created_at` comes from the database;
- a rollback of the surrounding action also removes the log row;
- business A can't see or write business B's rows;
- no business set → fails;
- `stock.adjusted` without a reason, or with a blank one, is rejected;
- `UPDATE`, `DELETE` and `TRUNCATE` as `app_runtime` fail with `42501` (style of `roles.test.ts`).

## 4. Guard test changes (not yet presented)

The P1.1 review minors, from PROGRESS. Each starts with a probe the current guard misses:
- the privilege rule uses `has_table_privilege('app_runtime', …)` instead of direct grants, and asserts `app_runtime` is a member of no role;
- cover every non-system schema, with `drizzle` (later `pgboss`) as listed exceptions;
- require the `business_id → businesses(id)` foreign key on every tenant table;
- pin `app_current_business_id()`: body, not `SECURITY DEFINER`, `STABLE`;
- an append-only rule: `entry_log` must have no UPDATE for `app_runtime` (listed table).
