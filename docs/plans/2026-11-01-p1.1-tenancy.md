# P1.1 Tenancy & Data Safety Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The first tables, `businesses` and `branches`, with Row-Level Security `FORCE`d, one way for code to work inside a business (`withBusiness`, `withNewBusiness`), and a guard test that fails if any table in `public` breaks the tenancy rules.

**Architecture:** Tables and their policies are declared in `packages/db/src/schema.ts` through small helpers. Migration `0001` is generated by drizzle-kit, then the policy function and the `FORCE` lines are added by hand. `packages/db/src/tenancy.ts` opens a transaction and sets `app.business_id` transaction-locally. Two integration test files on a throwaway PostgreSQL prove the behaviour and the guard. No API code changes.

**Tech Stack:** PostgreSQL 18 (`uuidv7()`, RLS), drizzle-orm 0.45 (`pgPolicy`), drizzle-kit 0.31, `pg` 8, Vitest 5 + Testcontainers (`startTestDatabase()` from `src/testing.ts`).

**Spec:** `docs/plans/2026-11-01-p1.1-tenancy-design.md`; ADR 0027 (this design), ADRs 0006, 0007, 0019.

## Global Constraints

- Role names `app_owner` (migrations, owns tables) and `app_runtime` (the app). `app_runtime` keeps SELECT, INSERT, UPDATE from migration `0000`'s default privileges; never DELETE or TRUNCATE.
- IDs: `uuid` with default `uuidv7()`. Timestamps: `timestamptz not null default now()`.
- Setting name: `app.business_id`. Function: `app_current_business_id()`, `LANGUAGE sql STABLE`, **not** `SECURITY DEFINER`, body `select nullif(current_setting('app.business_id', true), '')::uuid`.
- Policy name on every tenant table: `tenant_isolation`; permissive, `FOR ALL`, `TO public`, the same expression in `USING` and `WITH CHECK`: `<column> = (select app_current_business_id())`, where `<column>` is `id` on `businesses` and `business_id` everywhere else.
- `ENABLE` and `FORCE ROW LEVEL SECURITY` on every tenant table.
- Error codes the tests assert: `42501` (insufficient privilege, including RLS `WITH CHECK` failures), `22P02` (invalid uuid text), `23503` (foreign key).
- Never edit migration `0000`; never run `docker compose down -v` without the owner's OK (`CLAUDE.md` rule 7).
- Every new `.ts` file is under `packages/db/src` (already in both tsconfig `include`s); test files are excluded from the build by `tsconfig.build.json`.
- Docker Desktop must be running for the tests. Before each commit: gitleaks staged scan + personal-data search (`docs/devops/git-workflow.md`, Secrets). Conventional Commits, **no AI attribution lines** (`CLAUDE.md` rule 6).
- Write files with the Write/Edit tools or Git Bash, never PowerShell `Set-Content`/`Out-File` (BOM, CRLF).

## Decisions in this plan (and why)

| Decision | Why |
| --- | --- |
| Column and policy helpers (`id()`, `businessId()`, `createdAt()`, `tenantPolicy()`) live in `schema.ts`, not in `tenancy.ts` as the spec's §6 listed | `businessId()` references `businesses.id` and `tenancy.ts` imports the tables: keeping the helpers beside the tables avoids an import cycle. `tenancy.ts` holds only the transaction functions. (Spec §6 updated in Task 3.) |
| Edit the generated migration file rather than a separate `--custom` migration | The function must exist before the policies that call it, and `FORCE` belongs with its table. One file keeps them together and in order. |
| `withBusiness` accepts `NodePgDatabase` only, not a transaction | Calling it with a transaction would open a savepoint whose `set_config` outlives it, switching the business for the rest of the outer transaction. A type-level test pins this. |
| The guard checks grants to `PUBLIC` as well as to `app_runtime` | `app_runtime` gets every right granted to PUBLIC, so a `GRANT DELETE … TO PUBLIC` would bypass the rule. |
| No guard rule for plain views | With `FORCE`, a view owned by `app_owner` is filtered by RLS too. *(Corrected after the final review: materialized views and foreign tables are never filtered, so the guard refuses them under a `kind` rule; the review also added an extra-permissive-policy check and a `tenant_fk` rule for every key into a tenant table.)* |

## Review Focus

1. **A transaction passed to `withBusiness`** (nesting): must not type-check (Task 1, `@ts-expect-error` test).
2. **An empty-string business ID** (say, from a session with no business): `withBusiness(db, '', …)` → `22P02`, `work` not called (Task 1, same table as `'not-a-uuid'`).
3. **Two businesses' transactions at the same moment** on one pool: each sees only its own rows (Task 1).
4. **A valid UUID with no business behind it:** sees no rows; inserting a branch for it → `23503`, not a silent success (Task 1).
5. **`GRANT DELETE … TO PUBLIC`** on a tenant table: the guard reports it under `privileges` (Task 2 probe).

- [ ] **Step 1: Write the failing tests** in `src/tenancy.test.ts`

Setup (`beforeAll`): `startTestDatabase()`; `runtime = createDatabase(server.runtimeUrl, vi.fn())`; an owner `Pool`; a helper in the test file:

```ts
async function signUp(name: string): Promise<{ businessId: string; branchId: string }> {
  return withNewBusiness(runtime.db, async (tx, businessId) => {
    await tx.insert(businesses).values({ id: businessId, name });
    const [branch] = await tx.insert(branches).values({ businessId, name: `${name} main` }).returning();
    return { businessId, branchId: branch!.id };
  });
}
```

Create `a = await signUp('Shop A')` and `b = await signUp('Shop B')`. Tests (name → assertion):

- `sees only its own business and branches`: inside `withBusiness(a.businessId)`, `select` from `businesses` → exactly `[{ id: a.businessId, name: 'Shop A' }]` (pick `id`, `name`); from `branches` → only `a.branchId`.
- `cannot see or update another business's rows`: inside B, `select` from `businesses` → only B's row; `select` from `branches` `where id = a.branchId` → `[]`; `update(branches).set({ name: 'x' }).where(eq(branches.id, a.branchId))` → `rowCount` 0; inside A the name is still `'Shop A main'`.
- `refuses to insert a row for another business`: inside B, insert a branch with `businessId: a.businessId` → rejects `{ code: '42501' }`. (Drizzle wraps driver errors: assert on the `pg` error, e.g. `.rejects.toMatchObject({ cause: { code: '42501' } })` or whichever shape the wrapper exposes. Check once and use the same shape everywhere.)
- `refuses to move a row to another business`: inside B, `update(branches).set({ businessId: a.businessId }).where(eq(branches.id, b.branchId))` → `42501`.
- `shows nothing and refuses inserts when no business is set`: plain `runtime.db.select().from(branches)` → `[]`; plain insert into `businesses` → `42501`.
- `forgets the business when the transaction ends, on the same connection`: own `Pool({ connectionString: server.runtimeUrl, max: 1 })` + `drizzle(pool)`; after `withBusiness(a…)` commits, a plain `select` from `branches` → `[]` and does **not** throw; then a `withBusiness(a…)` whose `work` throws `new Error('boom')` rejects with `'boom'`, and a plain `select` afterwards → `[]`.
- `refuses a malformed business ID before running any work`: `it.each(['not-a-uuid', ''])` → `withBusiness(runtime.db, id, work)` rejects with `22P02`; `work` (a `vi.fn()`) not called.
- `keeps concurrent businesses apart`: `Promise.all` of `withBusiness(a…)` and `withBusiness(b…)`, each selecting `branches` after `select pg_sleep(0.1)`; each gets only its own branch.
- `sees nothing for a business that does not exist`: `withBusiness(runtime.db, '0190f0f0-0000-7000-8000-000000000000', …)`: `select` from `branches` → `[]`; inserting a branch with that `businessId` → `23503`.
- `filters the table owner too (FORCE)`: owner pool, `select count(*)::int as n from branches` → `[{ n: 0 }]`.
- `creates a business with a version-7 UUID`: `a.businessId` matches `/^[0-9a-f]{8}-[0-9a-f]{4}-7[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$/`.
- `it.each(['businesses', 'branches'])('refuses to delete from %s')`: runtime pool `delete from <table>` → `42501`.
- `does not accept a transaction in place of the database` (type-level, the test body can be empty): inside a `withBusiness` callback, `// @ts-expect-error a transaction would open a savepoint whose setting outlives it` on `withBusiness(tx, b.businessId, …)`. If a transaction *is* assignable to `NodePgDatabase`, the directive is unused and `pnpm typecheck` fails: then narrow `withBusiness`'s parameter until it isn't (e.g. require `NodePgDatabase & { $client: Pool }`), and say so in the commit.

### Task 2: The guard test

**Files:**
- Create: `packages/db/src/tenancy-guard.test.ts`

**Interfaces:**
- Consumes: the migrated schema from Task 1; `startTestDatabase()`.
- Produces: `findTenancyViolations(pool: Pool): Promise<Violation[]>` (local to the test file), `type Violation = { table: string; rule: 'rls' | 'force' | 'policy' | 'business_id' | 'privileges' | 'branch_fk' }`, sorted by `table`, then `rule`.

- [ ] **Step 1: Write the failing tests**

- `finds no violations in the real schema`: `expect(await findTenancyViolations(owner)).toEqual([])`.
- `reports each broken probe table under the right rule`: as `app_owner`, create a correct template table per probe (`id uuid primary key`, `business_id uuid not null references businesses(id)`, `ENABLE` + `FORCE`, the `tenant_isolation` policy exactly as in Global Constraints), then break exactly one thing each:

| Probe | Broken by | Expected rule |
| --- | --- | --- |
| `probe_no_rls` | `FORCE` but no `ENABLE` | `rls` |
| `probe_no_force` | no `FORCE` | `force` |
| `probe_no_policy` | no policy | `policy` |
| `probe_wrong_policy` | policy `USING (true) WITH CHECK (true)` | `policy` |
| `probe_select_policy` | policy `FOR SELECT` only | `policy` |
| `probe_no_business_id` | no `business_id` column; policy on `id` | `business_id` and `policy` (the policy names the wrong column) |
| `probe_nullable_business_id` | `business_id uuid` (nullable) | `business_id` |
| `probe_delete_grant` | `GRANT DELETE … TO app_runtime` | `privileges` |
| `probe_public_delete` | `GRANT DELETE … TO PUBLIC` | `privileges` |
| `probe_branch_fk` | extra `branch_id uuid references branches(id)` | `branch_fk` |
| `probe_good_branch_fk` | extra `branch_id uuid`, `foreign key (business_id, branch_id) references branches(business_id, id)` | none |

  Assert `toEqual` the exact sorted list for these probes; then drop them (`afterEach` or `finally`), and assert `finds no violations` again.

- [ ] **Step 2: Run to verify it fails**

Run: `pnpm --filter @business-software/db exec vitest run src/tenancy-guard.test.ts`
Expected: FAIL, `findTenancyViolations` not implemented (write it as a stub returning `[]` first: the real-schema test passes and the probe test fails with the whole expected list missing).

- [ ] **Step 3: Implement `findTenancyViolations`**

One SQL query per rule (or one query with `UNION ALL`), over tables in schema `public` with `relkind in ('r', 'p')`:

- `rls`: `not relrowsecurity`. `force`: `not relforcerowsecurity`.
- `policy`: no row in `pg_policy` with `polname = 'tenant_isolation'`, `polcmd = '*'`, `polpermissive`, `polroles = '{0}'` (PUBLIC), `pg_get_expr(polqual, polrelid) = pg_get_expr(polwithcheck, polrelid)`, and the expression containing `app_current_business_id()` and the tenant column (`id` for `businesses`, `business_id` otherwise).
- `business_id`: table is not `businesses` and has no `business_id` column of type `uuid` with `attnotnull`.
- `privileges`: `aclexplode(relacl)` has a grantee `'app_runtime'::regrole` or `0` (PUBLIC) with `privilege_type` not in `SELECT, INSERT, UPDATE`.
- `branch_fk`: has a `branch_id` column and no `pg_constraint` with `contype = 'f'`, `confrelid = 'branches'::regclass`, whose columns are (`business_id`, `branch_id`) → (`business_id`, `id`), in that order.
