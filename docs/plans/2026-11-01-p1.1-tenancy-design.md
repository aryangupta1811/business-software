## 1. Goal and success criteria

The first real tables, and the rule every later business table follows, so no module can see or write another business's rows even when its code is wrong.

Done means:
- `businesses` and `branches` tables with Row-Level Security, `FORCE`d;
- one way for code to run a transaction for a business (`withBusiness`), with the business set transaction-locally;
- a guard test that fails if any table lacks `business_id`, RLS, `FORCE` or a policy, or is granted DELETE/TRUNCATE;
- integration tests that try to read and write across businesses and must fail; no business set means no rows.

## 3. Database objects (migration `0001`) — presented, awaiting OK

**Tables:**

```
businesses  id uuid PK default uuidv7() · name text not null · created_at timestamptz not null default now()
branches    id uuid PK default uuidv7() · business_id uuid not null → businesses(id)
            · name text not null · created_at timestamptz not null default now()
            · unique (business_id, id)
```

- `unique (business_id, id)` on branches lets later branch-level tables (stock…) reference `(business_id, branch_id) → branches(business_id, id)`, so the database refuses a row of business A pointing at a branch of business B. RLS alone wouldn't catch that.
- Indexes start with `business_id` (ADR 0006).

**Function `app_current_business_id()`:** reads `current_setting('app.business_id', true)`, turns missing *or empty* into NULL (`nullif(…, '')::uuid`), returns uuid. Plain SQL, `STABLE`, **not** `SECURITY DEFINER`, so it runs with the caller's rights.

**Policies:** `businesses`: `id = (select app_current_business_id())`; `branches` and every future tenant table: `business_id = (select app_current_business_id())`. One policy for all commands, the same expression in `USING` and `WITH CHECK`, so you can neither insert another business's row nor move a row to another business. The `(select …)` wrapper makes PostgreSQL evaluate it once per query (an InitPlan), not per row. Policies apply to PUBLIC (with `FORCE`, the owner is filtered too).

**`FORCE ROW LEVEL SECURITY`** on both tables: owners otherwise skip RLS silently.

**Grants:** unchanged; P0.3's default privileges give `app_runtime` SELECT, INSERT, UPDATE and never DELETE.

**Migration form:** Drizzle generates the tables and policies from `schema.ts`; the function and the `FORCE` lines are added by hand to the same migration, with the function before the policies that call it. To check while implementing: editing the generated file vs `drizzle-kit generate --custom`; Drizzle can't generate `FORCE` (checked: drizzle-kit 0.31 knows `ENABLE ROW LEVEL SECURITY` only).

## 4. Code: `withBusiness` and data flow — not presented yet

To present: `withBusiness(db, businessId, async (tx) => …)` opens a Drizzle transaction, runs `select set_config('app.business_id', $1, true)` (`true` = transaction-local; `set_config` because `SET` takes no parameters), then the callback; the schema helper (tenant column + policy in one line); signup's order (generate the ID, set it as the current business, insert: no bypass needed); what P1.4 must solve (finding a user's business at login, before any business is set).

## 5. Tests — not presented yet

To present: the guard test over `pg_class`/`pg_policy`/`information_schema` (every table: `business_id` except `businesses`, RLS + FORCE, at least one policy, no DELETE/TRUNCATE for `app_runtime`); cross-business tests (read, update, insert as another business, moving a row; RLS refusals are `42501`); no business set → no rows and inserts refused; a pooled connection reused after a tenant transaction (the empty-string gotcha) with `max: 1`; delete still refused on the new tables; signup order works.

## Known gotchas (found in brainstorming)

- After a transaction-local `set_config` ends, the setting reads back as `''`, not NULL, on that connection; `''::uuid` throws. Handled by `nullif`.
- Signup is a chicken-and-egg: no business can be inserted before one is set. Handled by setting the new ID first.
