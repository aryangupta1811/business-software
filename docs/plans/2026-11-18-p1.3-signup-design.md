- **Status:** Approved. The owner gave the OK for the day's plans and answered the four questions in section 10 on 2026-11-18, all as recommended.
- **Requirements:** Module 00 (DECIDED): #1–11 (types, GST status, details), #14 (branch in another state), #21 (auto-lock), #27 (owner email login, unique across the app), #29 (staff idle), #31 (recovery key), #32 (email confirmed later).
- **ADRs it builds on:** 0003 (forms: React Hook Form + Zod), 0007 (data safety), 0008 (paise), 0009 (sessions, Argon2id), 0027 (tenancy), 0028 (entry log).
- **Plan:** `docs/plans/2026-11-18-p1.3-signup.md`

## 1. Goal and success criteria

A visitor fills one short form and gets a business, its first branch, an owner account and a recovery key, all in one transaction. The owner can later change the business's details, feature switches and lock times on a settings page.

Done when:

1. `POST /api/signup` creates the business, its first branch, the owner user, an unused recovery key and one `business.created` entry log row, together or not at all.
2. Signing up with an email that already owns a business answers `409 {code: "email_taken"}` and writes nothing, even when two signups with the same email race.
3. The recovery key is shown once, stored only as a hash, and is never in a URL, `localStorage` or a log.
4. Every request body goes through a shared Zod schema first: wrong lengths, unknown fields and the NUL character get a `400` with field error codes, never a `500`.
5. Every route names its permission or is marked public; a test fails if one doesn't. With no session (until P1.4), every non-public route answers `401`.
6. `recordEntry` refuses an action name that isn't in `ENTRY_ACTIONS`.
7. Signup, the recovery-key screen and settings work in English, Hindi and Hinglish, light and dark, at 1024 px, with no CSP violations.
8. The tenancy guard passes with the new tables; ADR 0027's rules hold.

## 3. Data (migration `0003`)

All new tables follow ADR 0027: `id()`, `businessId()`, `createdAt()`, `tenantPolicy(…)`, hand-written `FORCE ROW LEVEL SECURITY`, composite keys into tenant tables, `unique (business_id, id)` on referenced tables.

### `businesses` (new columns)

| Column | Type | Rule |
| --- | --- | --- |
| `business_type` | text | `check in ('kirana','medical','clothing','electronics','hardware')` (#1, #5) |
| `phone` | text | 10 digits, `check (phone ~ '^[1-9][0-9]{9}$')`; the form strips `+91`, a leading `0`, spaces and dashes |
| `gst_status` | text | `check in ('unregistered','regular','composition')` (#6) |
| `pan` | text, null | `check (pan ~ '^[A-Z]{5}[0-9]{4}[A-Z]$')` |
| `features` | text[] | enabled feature keys; the preset at signup (#1); Zod checks the names |
| `owner_lock_minutes` | smallint | default 5, `check between 1 and 30` (#21) |
| `staff_idle_minutes` | smallint | default 30, `check between 5 and 120` (#29) |
| `updated_at` | timestamptz | set on every settings save |

The columns are `NOT NULL` with no default where signup always supplies them. There are no real business rows yet (RDS has none; the live server keeps the skeleton until stage 7), so the migration needs no backfill. A local database with old test rows makes it fail loudly, never silently.

### `branches` (new columns)

Module 00 #14 says each branch has its own address and a branch in another state needs its own GSTIN, so the place-based details live on the branch:

| Column | Type | Rule |
| --- | --- | --- |
| `state_code` | text | the two-digit GST state code (`'27'` Maharashtra), `check (state_code ~ '^[0-9]{2}$')`; Zod checks it's a real one |
| `address` | text, null | ≤ 300 characters |
| `pin_code` | text, null | `^[1-9][0-9]{5}$` |
| `gstin` | text, null | 15 characters, format and check digit checked in `packages/shared`; its first two digits must equal `state_code` (a database `check` too) |
| `drug_licence` | text, null | medical (#8) |
| `fssai` | text, null | 14 digits, food/kirana (#8) |
| `updated_at` | timestamptz | |

Signup's "state" becomes the first branch's `state_code`. The first branch is named after the business; the owner can rename it in settings.

### `users` (new tenant table)

| Column | Type | Rule |
| --- | --- | --- |
| `id`, `business_id`, `created_at` | | ADR 0027 helpers; `unique (business_id, id)` |
| `role` | text | `check in ('owner','staff')` |
| `name` | text, null | the owner's name, filled later (#8) |
| `email` | text, null | `check (email = lower(btrim(email)))`; `check (role <> 'owner' or email is not null)` |
| `password_hash` | text, null | PHC string (section 5); null for staff without a login (#19, P1.5) |

**Owner email unique across the whole app (#27).** A partial unique index, `users_owner_email_unique on users (email) where role = 'owner'`. PostgreSQL checks unique indexes against every row, whatever RLS hides, so the second signup with an email fails with `23505` inside its own transaction and the API answers `409`. Signup needs **no cross-business read** and **no `SECURITY DEFINER` function**: the database refuses the duplicate. Two signups racing on one email are settled the same way: the second waits for the first's commit, then fails. P1.4's login-by-email function reads the same index.

This is the one deliberate unique key without `business_id` (P1.7 plans a guard rule requiring `business_id` in tenant unique keys; that rule gets an exceptions list with this index and its reason). ADR 0027 gets a dated note.

Staff usernames (P1.4/P1.5) will be a separate column, unique per business.

### `recovery_keys` (new tenant table)

`id`, `business_id`, `user_id` (composite key to `users`), `key_hash` (text: the SHA-256 as 64 lower-case hex characters, held to that by a check; changed from bytea while building, because hex compares and reads the same in SQL, the API and tests), `created_at`, `used_at` (null). A partial unique index allows **one unused key per user** (`(business_id, user_id) where used_at is null`). Module 00 #31 says a used key stops working and a new one is shown: P1.4 sets `used_at` and inserts the next one. Nothing is deleted (ADR 0007), so the history stays.

### `entry_log`

Adds the composite key `(business_id, actor_id) → users(business_id, id)` (ADR 0028's consequence: the task that creates users adds it). A NULL `actor_id` (the system) still passes. ADR 0028 gets a dated note.

## 4. Signup

### Form and request

Seven fields: business name, business type, phone, state, GST status, owner's email, password.

| Field | Rule (Zod, `packages/shared`) |
| --- | --- |
| `businessName` | trimmed, 1–100 characters, no control characters |
| `businessType` | one of the five types |
| `phone` | normalised to 10 digits as above |
| `stateCode` | one of the state codes |
| `gstStatus` | one of the three |
| `email` | trimmed, lowercased, ≤ 254, an email shape |
| `password` | 10–128 characters, not the email, not the phone number; never trimmed |

### `POST /api/signup` (`@Public()`)

Inside **one** `withNewBusiness` transaction:

1. insert the `businesses` row with the type's preset `features`;
2. insert the first branch;
3. hash the password (done *before* the transaction opens, so a slow hash doesn't hold a connection), insert the owner user;
4. make the recovery key, insert its hash;
5. `recordEntry(tx, { action: 'business.created', actorId: owner.id, entityType: 'business', entityId: businessId, after: {…fields, no password, no key} })`.

Answers:

- `201 { businessId, recoveryKey }`. The key leaves the server only in this one answer.
- `409 { code: 'email_taken' }`: the unique index refused it (`23505` on `users_owner_email_unique`; any other `23505` stays a 500).
- `400 { code: 'invalid_body', fields: { email: 'too_long', … } }`: error **codes**, which the web app translates; no English messages from the server.

**Idempotency (ADR 0007 rule 7).** Signup takes no idempotency key: the unique email already makes a retry unable to create a second business. If the `201` is lost on the way, the retry gets `409`, and the owner never saw the recovery key. P1.4 covers this: after login, an owner without a seen key can make a new one (password required). Noted for P1.4.

**Telling a visitor an email has an account** is accepted by #27 (scan item c). The signup rate limit arrives with P1.4's limiter before signup is ever deployed.

### Recovery key

- 160 random bits (`crypto.randomBytes(20)`), shown as **32 Crockford base32 characters in eight groups of four** (`7K3M-…`): no `I`, `L`, `O` or `U`, so it reads back without confusion.
- Stored as `sha256(key bytes)`. A slow hash like Argon2 protects *guessable* passwords; a 160-bit random key can't be guessed, so a fast hash is enough. Interview point.
- When used (P1.4), the owner types the email and the key: the login-by-email lookup finds the business, then an ordinary `withBusiness` lookup compares hashes with `timingSafeEqual`. The key itself carries no business ID.

## 5. Passwords (new ADR 0035)

- Node 24's built-in `crypto.argon2` (checked 2026-11-10: about 30 ms at 19 MiB and 2 passes, also in the ARM64 image). No native package or install script.
- Parameters: OWASP's Argon2id minimum (memory 19 MiB, 2 passes, parallelism 1), 16-byte random salt, 32-byte tag.
- Stored as a **PHC string**, `$argon2id$v=19$m=19456,t=2,p=1$<salt>$<hash>`, so the parameters travel with each hash and can be raised later (P1.4 rehashes at login when they're older).
- `verifyPassword` compares with `timingSafeEqual`; a malformed stored string fails closed.
- Tested against the published RFC 9106 Argon2id vector, so we know we call it correctly.
- The ADR also records the alternative (`argon2` npm package: native build, install script, `minimumReleaseAge` exposure) and why it lost.

## 6. API rules (new ADR 0036)

1. **Bodies.** Zod 4 schemas live in `packages/shared` (ADR 0002, 0003: one schema for the form and the server). A `ZodBodyPipe` in `apps/api` parses every `@Body()`. Schemas are `.strict()` (unknown fields refused). A shared `text(max)` helper trims, checks length and refuses `\u0000` and other control characters, so PostgreSQL never sees a NUL (scan item a). A test walks every controller and fails if a `@Body()` has no pipe.
2. **Permissions.** `packages/shared` exports `PERMISSIONS` (today `settings.view`, `settings.manage`); the owner has all of them. Each handler carries `@Permission('settings.manage')` or `@Public()`. A global guard:
   - refuses a route with neither (a coding mistake: `500` in tests, caught by a test that lists every route);
   - asks a `SessionResolver` for the caller. P1.3 ships `NoSessionResolver` (always "nobody"), so every non-public route answers `401` until P1.4 provides the real one. Tests swap in a fake resolver.
3. **Errors.** Client errors are Nest `HttpException`s with a `code`; everything else goes through `UnhandledErrorFilter` (messages only). Scan item (d): one test makes signup fail on a lost database and checks the single log line has the reason and no email, phone or password.

## 7. Business types and features

`packages/shared/src/business-types.ts`: the five types, the feature keys from Module 00's table, and each type's preset.

| Type | Preset feature keys |
| --- | --- |
| kirana | `loose_weight`, `expiry_dates`, `udhaar_prominent` |
| medical | `batches`, `expiry_dates`, `mrp`, `expiry_alerts` |
| clothing | `variants`, `exchanges`, `barcode_labels` |
| electronics | `serial_numbers`, `warranty`, `service_items` |
| hardware | `multiple_units`, `wholesale_price`, `large_credit` |

Later modules read `features` to show or hide what they build. Changing the type in settings **keeps** the current switches and offers one button, "Use the defaults for <type>", because mixed shops (#3, kirana + stationery) would lose switches they set.

## 8. Settings

`GET /api/settings` (`settings.view`) returns the business, its first branch and the owner's name. Three saves (`PUT`: each card is sent whole), each `settings.manage`, each one transaction with one `business.updated` entry (`before`/`after` of the changed fields only):

- `PUT /api/settings/business`: name, type, phone, GST status, PAN, owner name; branch name, address, PIN, state, GSTIN, drug licence, FSSAI
- `PUT /api/settings/features`
- `PUT /api/settings/security`: owner lock minutes, staff idle minutes

Old bills keep the details they were printed with (#11): that's P1.14's snapshot, so editing here is safe. Two counters saving at once: last save wins (both saves are logged). Acceptable for settings.

## 9. Web

- Routes split into two layouts: `_public` (signup, recovery key; a slim top bar with the language and theme switches, no sidebar) and `_app` (today's shell with the sidebar).
- **Signup** (`/signup`): two columns at ≥ 1024 px. Left, a quiet brand panel with three lines on what the app does. Right, the form: business type as five selectable cards with icons, GST status as three cards each saying which bill it issues (#6), state as a native `<select>` (type-ahead works), email and password with a show/hide button. React Hook Form + the shared Zod schema. A `409` puts "This email already has an account" under the email field.
- **Recovery key** (`/signup/recovery-key`): the key in large monospace groups, Print (a print stylesheet prints only the key, business name and date) and Copy buttons, and a checkbox "I have written down or printed this key" that enables Continue. The key lives only in memory: a refresh shows "For your safety the key is shown once. You can make a new one after you log in (P1.4)."
- **Settings** (`/settings`, sidebar item): three cards (Business, Features, Security), each with its own Save. Until P1.4, the page shows "Log in to see settings" on the `401`.
- Every string in `en`, `hi`, `hi-Latn`. New colour pairs, if any, go in `contrast.test.ts`.
- **P0.7 minors:** `min-h-*` instead of `h-14`/`h-10`; sticky sidebar and top bar; `readTokens` refuses a token that isn't 6-digit hex; `/design` heading levels fixed, plus an icon button and a tooltip example; `aria-keyshortcuts` on the Home link; the theme button's tooltip no longer repeats its label to screen readers; `readSavedTheme` used or removed.

## 13. Risks

- **Signup scope is large for one session.** If it runs long, settings (section 8, its page) moves to a second PR the same day; signup and the recovery key are the core.
- **Argon2 memory:** 19 MiB per hash; ten signups at once is 190 MiB on a 2 GB server. P1.4's rate limit caps it.
- **A lost `201`** leaves an owner without a seen recovery key; P1.4 must offer "make a new key" after login (noted above).
