- **ADRs it builds on:** 0007 (no deletes), 0008 (paise, basis points, thousandths), 0019 (ICU collation for item names), 0026 (shortcuts), 0027 (tenancy), 0028 (entry log), 0036 (Zod bodies, declared permissions).
- **Plan:** `docs/plans/2026-11-19-p1.7-items.md` (written after the OK)

## 1. Goal and success criteria

The owner can build the shop's catalogue: add, edit, find, archive and restore items, with units, prices, GST and barcodes. Billing (P1.13) and stock (P1.8) build on these tables without changing them.

Done when:

1. An item can be created, edited, archived and restored. Nothing is ever deleted, and each change writes one entry log row with `before` and `after` holding only the fields that changed.
2. A selling or wholesale price above the MRP is refused by both the shared schema and the database.
3. A barcode belongs to at most one live item or pack per business. A scan looks it up exactly, and unknown codes answer `404`.
4. Units follow #16: the 12 built-in units, the owner's own units (1 crate = 24 pieces), and buying in one unit while selling in another (a box of 12; 250 g from a 50 kg bag).
5. A caller without `items.view_cost` never receives the purchase price and can't change it.
6. Two counters editing the same item: the second save gets `409 stale` instead of silently overwriting the first.
7. Item names sort the same way locally and on RDS: Latin before Devanagari, "Atta 2 kg" before "Atta 10 kg", case ignored.
8. The guard rules from P1.1/P1.2 are in and prove themselves on broken probes, and every existing table still passes.
9. The Items page works in English, Hindi and Hinglish, light and dark, at 1024 px, with a scanner.

## 3. Units (#2, #16)

**Built-in units are constants in `packages/shared`, not rows.** No seeding at signup, no backfill, and every business has exactly the same 12. Each one has a code, a name in all three languages (in the i18n files), a **dimension**, and a fixed factor to its dimension's base unit where an exact one exists:

| Dimension | Units (factor to the base, in thousandths) |
| --- | --- |
| mass (base g) | `g` 1 000, `kg` 1 000 000 |
| volume (base ml) | `ml` 1 000, `litre` 1 000 000 |
| count (base piece) | `piece` 1 000, `pair` 2 000, `dozen` 12 000 |
| length | `metre`, `foot`: no conversion between them (0.3048 isn't a whole number of thousandths; nobody sells cloth by the foot) |
| pack | `box`, `pack`, `bag`: no fixed size; each item says what its box holds |

**The stock unit.** Every item has one `stock_unit`, which must be a built-in unit. Stock, prices and the low-stock level are all counted in it, with quantities in thousandths (ADR 0008). An item can be sold in its stock unit and in any unit of the same dimension with a fixed factor, so atta kept in `kg` can be sold as `250 g`, which is 250 thousandths of a kg. That conversion is done once, in a shared `toStockQuantity()`.

**Packs (`item_units`).** Packs are other units this item is bought or sold in, each with its own size in stock units: "box = 12 piece", "bag = 50 kg", "crate = 24 piece". A pack can have its own selling price, its own MRP and its own barcodes (a box's barcode is not a piece's). It can be marked "sold as a pack" (the counter can bill a box), "bought as a pack" (P2.1's purchase entry defaults to it), or both.

**Owner's own units (`units` table, #16).** A name, an optional Hindi name, a built-in base unit and a default size: 1 crate = 24 piece. Adding a crate pack to an item pre-fills 24, and the owner can change it for that item (question 3). Own units can be archived; nothing is deleted.

## 4. Data (migration `0005`; its number is fixed at rebase)

Every table follows ADR 0027: `id()`, `businessId()`, `createdAt()`, `tenantPolicy`, hand-written `FORCE`, composite keys into tenant tables, and `unique (business_id, id)` wherever another table points in. App code never runs `DELETE`.

### Collation `item_name` (ADR 0019's open point)

`CREATE COLLATION item_name (provider = icu, locale = 'und-u-kn-true')`: ICU's root order, deterministic, with numbers compared by value. Checked on `postgres:18` (PostgreSQL 18.6, ICU collation version 153.128) on 2026-11-19:

`Ácido | Amul | Atta 2 kg | atta 5 kg | Atta 10 kg | Basmati | अमूल | आटा | बासमती`

Latin comes before Devanagari, Devanagari is in Hindi dictionary order, and 2 comes before 10. The default `und-x-icu` puts "Atta 10 kg" before "Atta 2 kg". `items.name`, `items.hindi_name`, `categories.name` and `units.name` use this collation.

- **Not yet checked on RDS,** because it was stopped. On the next start, run the same query and compare the order and `collversion`. If ICU's version differs, the order can differ in rare characters; the index stays valid until a major upgrade, which then needs `REINDEX` (noted in `docs/devops/local-database.md`).
- Duplicate checks use `lower(name)`, not a non-deterministic collation. That stays simple and works with `LIKE`.

### `categories` (Module 00 #4: none pre-loaded)

`id`, `business_id`, `name` (1–60), `archived_at`, `created_at`, `updated_at`.

- `unique (business_id, id)`.
- Unique index on `(business_id, lower(name)) where archived_at is null`.

### `units` (owner's own units)

`id`, `business_id`, `name` (1–30), `hindi_name`, `base_unit` (a built-in code; check in the list), `default_size` (bigint thousandths of the base unit, > 0), `archived_at`, `created_at`.

- `unique (business_id, id)`.
- Unique index on `(business_id, lower(name)) where archived_at is null`.
- A check that the name isn't a built-in code.

### `items`

| Column | Type | Rule |
| --- | --- | --- |
| `id`, `business_id`, `created_at` | | ADR 0027; `unique (business_id, id)` |
| `kind` | text | `'goods'` or `'service'`. A service has no stock, MRP, packs or low-stock level (checks) |
| `name` | text `item_name` | 1–100, no control characters |
| `hindi_name` | text, null | 1–100; printed on Hindi bills (`02` #17) |
| `code` | text, null | the owner's short code for typing at the counter (question 6); 1–20, no spaces |
| `category_id` | uuid, null | `(business_id, category_id) → categories` |
| `brand` | text, null | 1–60. Free text; the form suggests brands already used |
| `stock_unit` | text | a built-in code (check in the list) |
| `selling_price` | bigint | paise, ≥ 0, per stock unit (retail) |
| `wholesale_price` | bigint, null | paise, ≥ 0 |
| `purchase_price` | bigint, null | paise, ≥ 0. The last known cost, used as the default for opening stock and the margin shown. Average cost is P1.8's |
| `mrp` | bigint, null | paise, > 0, per stock unit |
| `price_includes_tax` | boolean | default true (a shelf price) |
| `gst_rate` | integer, null | basis points, one of `GST_RATES` (question 1) |
| `hsn` | text, null | 4, 6 or 8 digits (the GST engine's rule); a service's SAC is 6 digits starting with 99 |
| `archived_at` | timestamptz, null | archived items don't show in billing or the default list |
| `version` | integer | starts at 1, +1 on every save; used for `409 stale` |
| `updated_at` | timestamptz | set on every save; index `(business_id, updated_at)` for P1.13's sync |

Database checks, repeating the shared schema so a bad write from any code path is refused:

- **MRP:** `mrp is null or (selling_price <= mrp and coalesce(wholesale_price, 0) <= mrp)`.
- **An item with an MRP must have a tax-inclusive price** (`mrp is null or price_includes_tax`). By law the MRP includes every tax, so comparing an inclusive price with it is exact. With a price before tax, the GST rounding could push the customer's total a paisa over the MRP. This is question 2.
- **No duplicate names:** unique index on `(business_id, lower(name)) where archived_at is null` (question 5).
- **Unique short code:** unique index on `(business_id, lower(code)) where code is not null and archived_at is null`.
- **Services:** `kind = 'goods' or (mrp is null)`. The pack and level tables check the item's kind through a composite key on `(business_id, id, kind)`.

**GST is required by the API, not the database,** for a business whose GST status is `regular` (G5: every line of a tax invoice needs a rate and an HSN code). The status lives on another table and can change, so a database check can't hold it. P1.14 refuses a bill whose item has none, so an item saved while the business was unregistered can't slip through after it registers. For `composition` and `unregistered` businesses, the rate and HSN code are optional and shown as "needed if you register for GST".

### `item_units` (packs)

`id`, `business_id`, `item_id` (composite key to `items`), `unit_code` (built-in, null) **or** `unit_id` (owner's unit, composite key, null), with a check that exactly one is set. Also:

- `size`: bigint thousandths of the item's stock unit, > 0.
- `selling_price`, `mrp`: null means "size × the item's price" and "no pack MRP".
- `sold_as_pack`, `bought_as_pack`: booleans.
- `archived_at`, `created_at`.

Constraints:

- `unique (business_id, id)`.
- One live pack per unit per item: unique `(business_id, item_id, coalesce(unit_code, unit_id::text)) where archived_at is null`.
- The same MRP check as items.

### `item_barcodes`

`id`, `business_id`, `item_id`, `item_unit_id` (null means the stock unit), `code` (printable ASCII, no spaces, 4–48 characters), `in_store` (true for codes the app made), `removed_at`, `created_at`.

- **One live owner per code:** unique `(business_id, code) where removed_at is null`. A code stays attached to an archived item, so scanning it says "archived — restore?". To give the code to a new item, remove it from the old one first (`removed_at`, logged).
- More than one barcode per item is allowed: manufacturers change codes, and old stock keeps the old one.
- **In-store codes (#8, loose and unbranded items):** EAN-13 in the GS1 in-store range (starts with `2`) with a valid check digit. The next number comes from the highest existing in-store code, read under a lock on the business row, so two counters can't make the same one. A unique-index violation is the backstop.
- Manufacturer codes aren't checked for a check digit. A scanner returns what's printed, and some local packs print codes that don't follow EAN.

### `item_branch_levels` (#1: low-stock level per branch)

`id`, `business_id`, `item_id`, `branch_id` (both composite keys), `low_stock_level` (bigint thousandths, ≥ 0), `updated_at`. Unique `(business_id, item_id, branch_id)`. One row per item per branch, created when the owner sets the level.

### Entry log actions (`ENTRY_ACTIONS`, reason optional)

`item.created`, `item.updated`, `item.archived`, `item.restored`, `item.barcode_added`, `item.barcode_removed`, `category.created`, `category.updated`, `category.archived`, `unit.created`, `unit.updated`, `unit.archived`.

- An update's `before`/`after` hold only the fields that changed, prices included. P2.6's flag for a price lowered and raised back on the same day (sitting 2, L flags) reads these.
- The log holds the purchase price, so **P2.6 must hide `purchase_price` from viewers without `items.view_cost`**. This gets added to P2.6's notes.

## 5. Permissions (ADR 0036)

New in `PERMISSIONS`. The owner has all of them, and P1.5 lets the owner give staff a subset (Module 00 #17).

| Permission | Allows |
| --- | --- |
| `items.view` | list, search, barcode lookup, read one item |
| `items.manage` | create, edit, archive and restore items; categories, own units, packs, barcodes, levels |
| `items.view_cost` | see and change `purchase_price` (#1: hidden from staff unless the owner allows) |

Without `items.view_cost`:

- the purchase price is **left out of the answer entirely**, not set to null, and a test checks that the key is absent;
- a body that includes it is refused with `403`;
- an edit keeps the stored value.

## 6. API

Bodies use strict Zod schemas from `packages/shared/src/items.ts`. Prices travel as integer paise, and the form converts them with `parseRupees`. Every response is built from the same shared types.

| Route | Permission | Does |
| --- | --- | --- |
| `GET /api/items?q=&category=&archived=&after=` | `items.view` | Search and list, 50 at a time, sorted by `name collate item_name, id` with a keyset `after` cursor |
| `GET /api/items/:id` | `items.view` | One item with its packs, barcodes and the levels for each branch |
| `GET /api/items/barcode/:code` | `items.view` | Exact lookup: `{ item, packId \| null }`, or `404 unknown_barcode`. An archived item comes back marked as archived |
| `POST /api/items` | `items.manage` | Create an item with its packs, barcodes and levels in one transaction |
| `PUT /api/items/:id` | `items.manage` | Save the whole item with `version`. `409 stale` if someone saved first |
| `POST /api/items/:id/archive`, `/restore` | `items.manage` | Set or clear `archived_at`. Restoring checks the name and short code are still free (`409 name_taken`) |
| `POST /api/items/:id/barcodes`, `POST /api/items/:id/barcodes/:barcodeId/remove` | `items.manage` | Add a barcode (`409 barcode_taken` with the other item's name), or remove one |
| `POST /api/items/barcodes/in-store` | `items.manage` | Make the next in-store code (not saved until it's attached to an item) |
| `GET/POST/PUT /api/categories`, `/api/units` (+ `/archive`) | `items.view` / `items.manage` | Categories and own units |

**Search.** `q` matches the short code exactly, a barcode exactly, and `name`, `hindi_name` and `brand` by "contains" (`ILIKE`, with `%` and `_` escaped). Matches starting with the term come first.

- No `pg_trgm` index for now. A shop's catalogue is a few thousand rows, and the query filters on `business_id` first, so a scan is a few milliseconds.
- If a demo business with tens of thousands of items shows it's slow, the next step is a trigram index (a trusted extension; check that `app_owner` can create it on RDS).
- Hinglish search ("aata" finding आटा) is out of scope; it goes to the ideas backlog.

**Errors.** Errors are codes, as in ADR 0036: `name_taken`, `code_taken`, `barcode_taken`, `above_mrp`, `mrp_needs_inclusive_price`, `gst_required`, `stale`, `unknown_barcode`. The unique-index names map to the codes. Any other `23505` stays a `500`.

**Concurrency.** `PUT` runs `update … where id = $1 and version = $2 returning …`. Zero rows means `409 stale`, and the form offers to reload. Two counters adding the same barcode or name at once: the index refuses the second one with `409`.

## 7. Items page (web)

- **`/items`** (sidebar item, `Alt+I`):
  - a search box (focused on `/`) with category and "show archived" filters;
  - a table with name (Hindi name under it), short code, category, unit, selling price, MRP and GST rate, sorted by name;
  - an "Add item" button (`Alt+N`).
  - The cost column shows only with `items.view_cost`.
- **The scanner on this page:** a scan with no field focused (ADR 0026's scanner-safe handling) opens that item, or if it's unknown, a new item with the barcode filled in. A scan in the search box searches.
- **Item form** (`/items/new`, `/items/$id`), one page in three cards:
  1. **Basics:** kind, name, Hindi name, short code, category (pick or "add new"), brand (suggestions).
  2. **Price and tax:** stock unit, selling price, wholesale price (shown with the `wholesale_price` feature), purchase price (with `items.view_cost`), MRP, "price includes GST", GST rate (a select from `GST_RATES`), HSN.
     - The form shows the margin and "price with GST" as you type, using the GST engine for one line.
     - It warns before save when the price is above the MRP.
  3. **Packs, barcodes and low-stock levels:** packs (shown with `multiple_units` or once any pack exists), barcodes with "Make an in-store code", and the level per branch.
- React Hook Form and the shared schema. `409` errors are shown under their field. Archive and restore use a native `<dialog>` confirm (ADR 0026), never `window.confirm`.
- **Features only hide fields; the API accepts them either way.** Switching a feature off never makes stored data invalid.
- **Categories and units** are managed in a small "Categories & units" tab on the Items page, not in Settings.
- Every string is in `en`, `hi` and `hi-Latn`. Built-in unit names are translated; owners type their own units' names.

## 8. Guard rules carried in (P1.1, P1.2 review minors)

In `packages/db/src/tenancy-guard.test.ts`, each with a broken probe that the test must report:

1. **`unique_business`:** every unique constraint or unique index on a tenant table includes `business_id` among its key columns, except the primary key on `id` and the listed exception `users_owner_email_unique` (ADR 0027's note gives the reason). Indexes on expressions count `business_id` if it's one of the plain columns.
2. **`append_only_missing`:** each `APPEND_ONLY` name exists (`to_regclass`), and the append-only rule also covers each listed table's partitions (`pg_partition_tree`).
3. **`fk_not_valid`:** `business_fk`, `branch_fk` and `tenant_fk` keys must be validated (`convalidated`), so a `NOT VALID` key no longer passes.
4. **`schema_usage`:** `app_runtime` has no `USAGE` on any `NOT_TENANT_SCHEMAS` entry. **Coordination with lane 3 (P1.4):** its rate-limit and email-lookup tables need a schema the app *can* use (P1.4 note g). They go in a separate, named list with their own rule, not `NOT_TENANT_SCHEMAS`, so this rule doesn't block them. Whichever lane merges second adapts.
5. **`entry-log.test.ts` no longer depends on test order:** each test makes its own businesses and reads rows by ID.

## 9. Room left for P1.8 and P1.10

- **P1.8:** stock movements reference `(business_id, item_id)` and count thousandths of `stock_unit`. A pack sale is converted with the pack's `size`. The item's `kind = 'service'` means no stock rows. `purchase_price` seeds the first average cost.
- **P1.10:** a batch table with its own MRP and expiry; when present, the batch MRP is the one billing checks. A variant table with its own barcodes: `item_barcodes` gains a nullable `variant_id`. A serial-number table. None of them change the P1.7 columns.

## 10. Tests (every business rule)

**`packages/shared` (unit):**
- Unit conversions: kg↔g, litre↔ml, dozen and pair to piece; no conversion between length units or for pack units without a size; rounding refused when a quantity isn't a whole number of thousandths.
- `toStockQuantity` for a pack and for a fixed-factor unit.
- The item schema:
  - prices in paise ≥ 0;
  - MRP ≥ the selling and wholesale prices, on the item and on each pack (the effective pack price is size × price when it has no own price);
  - an MRP requires a tax-inclusive price;
  - the GST rate is in `GST_RATES`;
  - the HSN code is 4, 6 or 8 digits, and a service's SAC is 99xxxx;
  - names have no control characters (ZWJ/ZWNJ allowed for Hindi);
  - unknown fields are refused;
  - the purchase price key is refused in the staff variant.
- The in-store EAN-13 check digit against published examples.

**`packages/db` (Testcontainers):**
- Every database check, by inserting a bad row: above MRP, MRP with an exclusive price, a service with an MRP, a pack with both or neither unit, a negative price, a size of 0.
- The partial unique indexes: a name is reusable after archiving, case is ignored, and a barcode is reusable after `removed_at`.
- Cross-business:
  - business B can't attach a category, unit, item or branch of business A (composite keys);
  - B's barcode lookup never sees A's code;
  - the same barcode and the same name in two businesses both succeed.
- The `item_name` collation order (the sample above).
- The guard probes for the four new rules.

**`apps/api`:**
- Create, edit, archive and restore, each with its one entry log row and the changed fields only.
- `409 stale` on a stale `version`.
- Two concurrent adds of the same barcode: one `201`, one `409 barcode_taken`.
- The purchase price is absent from list, search, one-item and barcode answers without `items.view_cost`. A body with it answers `403`, and an edit without it keeps the stored value.
- `gst_required` for a regular business, optional for composition and unregistered.
- Search: exact code and barcode first, then prefix, then contains; `%` and `_` in `q` are literal; archived items hidden unless asked for; keyset pages have no gaps or repeats.
- In-store codes: two at once give two different numbers.
- The route census picks up the new controllers (ADR 0036).

**`apps/web`:**
- The form: field errors from codes in three languages, price with GST and margin shown as you type, the MRP warning, the cost field hidden without the permission, a `409` under the right field.
- The scanner on the page: an unknown code opens a new item with it filled in.

**Real-app check in Chrome:** three languages, light and dark, 1024 px, a USB scanner (or a typed burst), the database rows and the entry log, no CSP violations.

## 11. Questions for the owner

Each has a recommended answer. Questions 1 and 4 touch DECIDED text (G1 and `01`'s summary line); the others fill in details the requirements leave open.

1. **GST rates and G1.** G1 recommended "P1.7 checks the item's HSN code carries that rate". That needs the government's HSN-to-rate table: thousands of rows that change by notification, and no official machine-readable copy to depend on.
   - **Recommend:** P1.7 checks the rate is one of today's rates, `GST_RATES`, and checks the HSN code's format. The owner (or their CA) picks the rate.
   - *Unverified:* the exact list after GST 2.0 (September 2025) must be checked against CBIC's rate notifications when building. The list lives in one constant.
   - An HSN-to-rate suggestion list can be an idea for later.
2. **MRP needs a tax-inclusive price.** Recommend yes. MRP includes all taxes by law, so this makes "never above MRP" exact to the paisa. Items without an MRP may use either kind of price.
3. **Own unit sizes per item.** Recommend: an owner's unit (crate = 24 pieces) pre-fills its size, and the owner can change it for one item (a crate of bottles vs a crate of eggs). Otherwise the owner would need "crate-24" and "crate-30" as separate units.
4. **"Prices per branch."** `01`'s summary line says items track "units, prices, GST and stock per branch".
   - **Recommend:** one catalogue and one price list for the whole business; stock (P1.8) and the low-stock level per branch.
   - Branch-specific prices can be added later as an override table without changing these columns.
   - If you agree, the summary line gets a Change log entry saying "stock per branch; prices per business".
5. **Two live items with the same name.** Recommend refusing it (case ignored), so billing search never shows two identical rows. Sizes go in the name ("Atta 5 kg", "Atta 10 kg"); an archived item frees its name.
6. **A short item code** (not in #1's field list). Recommend adding it as optional: typing "112 Enter" at the counter is faster than searching for items without a barcode. Unique per business.
7. **Item kind "service"** (repair charge, delivery fee; product overview and the electronics preset). Recommend adding it in P1.7: no stock, MRP or packs; SAC instead of HSN.
8. **In-store barcodes now, label printing later.** Recommend P1.7 makes and stores in-store codes, and P1.15 prints the labels with the other printing work.

### Changed while building (2026-11-19)

- **In-store codes are made and attached in one call** (`POST /api/items/:id/barcodes` with `code: null`), under a lock on the business row. A separate "make the next code" route can't reserve a code it hasn't saved, so two counters could both get the same one. Codes count from the highest ever made, removed ones included, so an old label never scans as a different item.
- **Item tables default `business_id` to the transaction's business** (as `entry_log` does). Services never pass it.
- **The collation is used in queries, not set on columns.** drizzle-kit 0.31 can't declare a column collation, and the unique indexes use `lower(name)` anyway.
- **No `(business_id, id, kind)` key** to stop a service from having packs in the database. A key on `kind` would block turning an item with archived packs into a service. The shared schema refuses packs, levels and an MRP on a service, and an update archives the packs a service no longer sends.
- **A level left out of an update goes back to 0** (no alert): rows are never deleted.
- **Guard item 5** (order-independent `entry-log.test.ts`) was already done in P1.3: each test counts rows before and after, and the isolation test makes its own empty business.
- **The Items page** goes in a second PR on the same day (section 13's split), so the data and API can merge first.

### Review fixes (2026-11-19, PR #31)

- **Saving packs parks moving ones first.** The live-unit unique index checks each write, not the final set, so two packs swapping units, or a new box listed before the old box becomes a dozen, collided half-way (`409 duplicate_pack`) though the final set was valid. Packs whose unit changes are archived together, then every sent pack is written live again, then new ones are added.
- **`in_store` is true only for codes the app made.** It was set from the code's pattern, so a typed or scanned 2-prefixed EAN-13 (weighing scales print them) counted as ours; the highest possible one made the next in-store code fail for good. Making a code now also skips any code already used, live or removed.
- **Cursors are checked strictly** (rank 0-2, a valid item name, a real UUID) before they reach PostgreSQL, so a forged one answers `400`, never a `500`.
- **A dropped pack's barcodes** are listed in that save's `item.updated` log row (`before.barcodes`).
- **Removing a barcode** locks the item and refuses an archived one (`409 archived`), like adding one.
- **G5 answers the field code `gst_required`** (under `gstRate` and `hsn`), as section 6 says, instead of `required`.
- **Renaming or archiving an own unit** marks the items using it as changed (`updated_at`), since each pack shows its unit's name and P1.13 syncs what changed.
- Fewer queries: one insert for a new item's barcodes, new packs and levels; `update` doesn't reload the item a third time. One shared check each for UUIDs (`isUuid`) and barcodes (`barcode()`).

### The Items page as built (2026-11-19, PR 2)

- **`GET /api/items/context`** (`items.view`): the caller's `canViewCost` and `canManage`, `needsGst` (G5), the business's features and its branches. The page needs these before it shows a form, and it can't read settings (owner only) or permissions (P1.5) yet.
- **Scans:** a burst of at least four printable characters, each within 50 ms of the last and ended by Enter, with no field focused, is a scan (`apps/web/src/items/scan.ts`). Shift (for capitals) doesn't break a burst. A known code opens its item; an unknown one opens a new item with the code filled in (only for someone with `items.manage`). A scan into the search box is ordinary typing, so it searches.
- **`/` focuses the search box.** ADR 0026's keys allowed only F-keys, Escape, `?` and Ctrl/Alt combos; `/` is now allowed too, matched by the key's position (Inscript types "य" there), and like `?` it fires only outside fields.
- **The form checks the body with the API's own schema** (`itemResolver`), so errors appear under their fields before a request is sent; Zod runs the cross-field rules (MRP, packs) once every field passes its own check, as on the API.
- **A saved item's barcodes are added and removed at once**, not with Save, so a code scanned at the counter works straight away. Barcodes for a pack are API-only for now (the page adds codes for the stock unit).
- **Not in this PR:** editing an own unit (archive it and add it again), brand suggestions, and the price-history view.
