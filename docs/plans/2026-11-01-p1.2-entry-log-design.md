# P1.2 Entry Log Recording — Design Spec

**Status:** approved section by section by the owner (sessions 13–14, 2026-11-01 and 2026-11-02); this file awaits the owner's review before the implementation plan is written.
**Task:** P1.2 in `docs/PROGRESS.md`. **Related ADRs:** 0007 (rule 2: append-only; rule 3: one transaction per action), 0019 (default privileges), 0027 (tenancy). New ADR: 0028 (entry log).
**Requirements used:** `00` #20 (every action is recorded against the logged-in person), `01` #11 (stock adjustments carry a reason), Module 06 (still DRAFT: only the recording side is built here; the viewer and the unusual-activity flags wait for `/finalize-module 06`).

## 1. Goal and success criteria

From the first feature that changes data, every change gets one permanent log row: who, what, when, old value → new value. The viewer is P2.6. Recording comes first, or the early history is missing.

Done means:
- a tenant table `entry_log` that `app_runtime` can only insert into and read;
- one helper, `recordEntry(tx, entry)`, that every module calls inside its own transaction;
- tests for every rule in sections 3 and 4;
- the guard test closes the P1.1 review gaps (section 5);
- `pnpm check` green.

Owner's answers (2026-11-01):
- **Who:** `actor_id` is a nullable UUID with **no foreign key yet** (option A). NULL means the system (e.g. the worker). P1.4 adds the users table and a migration adds the composite key. Rejected: a minimal `users` table now (pulls P1.4 in), a free-text name (weak evidence).
- **Old → new:** two `jsonb` columns, `before` and `after` (option 1). Rejected: one row per changed field (a 20-line bill becomes a pile), a single `{field: [old, new]}` (every module would compute the diff, and a mistake would corrupt history silently).
- **Retention:** rows are kept forever (assumption, not corrected; revisit at `/finalize-module 06`).

Out of scope: the viewer, filters and indexes for it (P2.6), flags for unusual activity, the users table and the actor's foreign key (P1.4), wiring any real module (none changes data yet).

## 3. The table `entry_log` (approved)

| Column | Notes |
| --- | --- |
| `id` | UUIDv7 via `id()` |
| `business_id` | `businessId()` plus a default of `app_current_business_id()`, so the helper never passes it and can't write to another business |
| `branch_id` | uuid, optional; composite key `(business_id, branch_id) → branches(business_id, id)` (the guard demands it) |
| `actor_id` | uuid, nullable, no foreign key yet; NULL = the system |
| `action` | text, not null, such as `stock.adjusted`; not a database enum, because a new action would need a migration |
| `entity_type` | text, not null, e.g. `item` |
| `entity_id` | uuid, not null (every ID in the app is a UUIDv7) |
| `reason` | text, optional |
| `before`, `after` | jsonb, optional |
| `created_at` | `createdAt()`, set by the database |

- Standard tenant table: `tenantPolicy(t.businessId)`, `ENABLE` + hand-written `FORCE ROW LEVEL SECURITY` in the migration.
- **Append-only:** the migration runs `REVOKE UPDATE ON entry_log FROM app_runtime`. DELETE and TRUNCATE are already missing from the default privileges (P0.3).
- No new function, so nothing to revoke from PUBLIC.
- `app_owner` owns the table and could still update it. It is the migration role and never runs at runtime (ADR 0007 restricts only the runtime role).

## 4. The write helper `recordEntry` (approved)

In `packages/db/src/entry-log.ts`:

```ts
await withBusiness(db, businessId, async (tx) => {
  // ...the business action itself...
  await recordEntry(tx, {
    actorId, // string | null, required (null = the system)
    action: 'stock.adjusted',
    entityType: 'item',
    entityId: itemId,
    reason: 'Damaged in transit',
    before: { quantity: 10 },
    after: { quantity: 8 },
  });
});
```

- **Takes a `Transaction`, not the database:** it can't be called on its own, so the log row and the action commit or roll back together (ADR 0007 rule 3).
- **`actorId` is required but may be `null`:** forgetting "who" is a type error; "the system" has to be written on purpose.
- **Actions are a typed list in `packages/db`** (`packages/db` doesn't depend on `packages/shared`, and one list isn't worth a new dependency; human-readable labels for the viewer can go in `shared` in P2.6):
  ```ts
  export const ENTRY_ACTIONS = {
    'stock.adjusted': { reasonRequired: true }, // Module 01 #11
  } as const satisfies Record<string, { reasonRequired: boolean }>;
  export type EntryAction = keyof typeof ENTRY_ACTIONS;
  ```
  Each later module adds its names here. A typo is a type error.
- **Reasons:** for an action with `reasonRequired`, a missing or blank (whitespace-only) reason throws before the database is touched. For other actions, a blank reason is stored as NULL.
- **`branchId`** is optional in `EntryInput`.
- **`before`/`after`** are plain JSON objects, optional; money inside is integer paise (ADR 0008). They go through `JSON.stringify` before the insert, so a value that can't become JSON (a `BigInt`, a cycle) throws and nothing is written.
- **It only writes.** No read function (the viewer is P2.6); tests read the table directly.
- **No business set:** `business_id` defaults to NULL and the insert is refused (NOT NULL, and the policy's check).

**Tests** (`src/entry-log.test.ts`, Testcontainers like the other db tests):
1. A recorded row has every field as given; `business_id` is the current business; `created_at` comes from the database.
2. The surrounding action rolls back → the log row is gone too.
3. Business A can't read business B's rows; an insert with B's `business_id` from inside A's transaction is refused.
4. An insert with no business set fails.
5. `stock.adjusted` with no reason, `''` or `'   '` throws, and no row is written.
6. As `app_runtime`: `UPDATE`, `DELETE` and `TRUNCATE` on `entry_log` fail with `42501` (Drizzle wraps errors: the code is on `error.cause.code`; on a raw `pg` Pool it's `error.code`).
7. A branch from another business is refused by the composite key.
8. `before` with a `BigInt` throws and writes nothing.

## 5. Guard test changes (approved)

The P1.1 review minors. Each starts with a probe the current guard misses (red), then the fix (green).

| Change | The gap today | Probe |
| --- | --- | --- |
| Privileges via `has_table_privilege('app_runtime', oid, …)` for DELETE, TRUNCATE, REFERENCES, TRIGGER, MAINTAIN | only direct grants are read; a grant to a role `app_runtime` belongs to slips past | grant DELETE to a helper role, make `app_runtime` a member |
| `app_runtime` is a member of no role | membership is how privileges are inherited | separate check: no `pg_auth_members` row with `member = app_runtime` |
| Every non-system schema, not only `public` | a tenant table in another schema is never checked | a table in a probe schema with RLS off; `drizzle` (later `pgboss`) listed as exceptions with reasons |
| `business_id → businesses(id)` foreign key required | a `business_id` with no key passes, so it can hold a made-up business | `business_id uuid not null` without `references` |
| Append-only tables have no UPDATE | the rule allows SELECT, INSERT and UPDATE everywhere | a list `appendOnly = ['entry_log', …]`; a probe on that list that still has UPDATE |
| Pin `app_current_business_id()` | its body could change, or it could become `SECURITY DEFINER`, and nothing fails | one check on `pg_proc`: exact body, `STABLE`, not security definer |
| No `SECURITY DEFINER` function that PUBLIC can execute | such a function runs with its owner's rights; executable by anyone, it's a way around RLS. P1.4's login lookup will need one | a probe function with default EXECUTE |

System schemas skipped: `pg_catalog`, `information_schema`, `pg_toast` and anything starting `pg_`.

## 6. Risks
