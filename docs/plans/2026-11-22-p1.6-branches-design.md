## 1. Goal and success criteria

A shop owner with two or more shops runs them from one account: each shop is a branch with its own counters, stock, staff and invoice numbers, and the owner can look at one branch or all of them together.

Done when:

1. The owner adds a branch (name, address, PIN, state, GSTIN, licences) and edits it in Settings. A business with one branch sees nothing new until it adds a second (`01` #13's rule).
2. Every counter computer belongs to one branch. Everything done on it (bills, stock changes, held bills, the entry log) is recorded at that branch, and the bill prints that branch's address and GSTIN.
3. The owner picks which branch a read page shows (Stock, the stock column on Items, later the dashboard and the entry log), including **All branches** where the page can combine them (#13).
4. Staff log in only on a computer at their home branch or at a branch the owner allowed (#35), and see only the branch they're logged in at.
5. Each branch has its own invoice series, so two branches never print the same number in one year (section 6).
6. A branch is archived, never deleted (ADR 0007); its history stays readable.
7. One business never sees another's branches (a test over two businesses).

## 3. How it works today

- Signup creates the business and its first branch (P1.3). `branches` already has `name`, `state_code`, `address`, `pin_code`, `gstin`, `drug_licence`, `fssai`, with the composite key every branch-level table uses.
- Settings edits "the business details", which are the business row plus **the first branch** (`settings.service.ts`, "The first branch, until P1.6").
- The owner's first login on a computer registers it (`devices`) on **the first branch** (`session.service.ts`, `startIn`). A session takes its computer's branch, and `Caller.branchId` is that branch for every request: stock adjustments, held bills and the entry log already use it.
- The Stock page already lists an item's stock at every branch.

So the data model is already branch-aware. P1.6 adds the ways to have more than one branch and to choose between them.

## 4. Approaches: which branch a person is working in

This is the main design choice. Three ways:

- **A. The computer decides; the owner's picker is for looking.** **Recommended.** Every write happens at the computer's branch, as today. The owner gets a branch picker in the top bar that changes only what read pages show, including All branches. A bill made at the Andheri counter is always an Andheri bill, with Andheri's address and invoice number, whoever is logged in. It matches the shop: the counter is physically in a branch. It needs no change to `Caller.branchId` or to any write route.
- **B. The owner's picker switches the session's branch for everything**, billing included. The owner could sell "as Thane" from the Andheri counter, printing Thane's address on a bill handed over in Andheri. It is wrong for GST (the place of supply follows where the goods are) and confusing for stock.
- **C. A branch box on every write form.** The most flexible, and the most chances to save something at the wrong branch. Later modules that genuinely need it (purchases entered at the head office for another branch, Module 04, DRAFT) can add a box on that one form.

With A, a page that reads branch data takes an optional `?branch=` (an id, or `all` where the page supports it). The owner may ask for any branch; staff get only their session's branch, whatever they send. Without it, a page shows the computer's branch.

## 5. Data

### `branches` (new columns, one migration)

| Column | Type | Rule |
| --- | --- | --- |
| `code` | text, not null | A short code for invoice numbers and lists, e.g. `AND`, `THN`. 1 to 6 capital letters or digits, `unique (business_id, code)`. The migration fills the existing first branch with `HO`. |
| `archived_at` | timestamptz, null | Archive, never delete. |
| (head office) | | The first branch (oldest `created_at`) is the head office: the business's details and GSTIN rule (#36) belong to it. It can't be archived. Not a column; a rule in the service and a test. |

GSTIN: the existing check (`left(gstin, 2) = state_code`) already enforces #14. A new branch in the same state as another is prefilled with that branch's GSTIN and can be changed (a business may hold more than one registration in a state). My call, not a question.

### `devices`

`branch_id` exists. Moving a computer to another branch updates it, ends the sessions open on that computer, and logs `device.moved` (before → after branch).

### `staff_branches` (new table)

`business_id`, `user_id`, `branch_id`, `created_at`. Composite keys to `users` and `branches`, `unique (business_id, user_id, branch_id)`, RLS like every table. It holds the **extra** branches a staff login may work at; the home branch is always allowed and is not repeated here. A row is removed when the owner unticks a branch. This is permission data, not a business record; every change is in the entry log, so nothing is lost (ADR 0007 covers business records). A reviewer may prefer an `ended_at` column instead; either works.

### Entry log, new `ENTRY_ACTIONS`

| Action | When |
| --- | --- |
| `branch.created`, `branch.updated` | branch added or changed (changed fields only) |
| `branch.archived`, `branch.restored` | archive and bring back |
| `device.moved` | a computer moved to another branch |
| `staff.branches_changed` | a staff login's extra branches changed |

## 6. Invoice numbers per branch

`architecture.md` already puts the invoice counter per **(branch, financial year)**, taken under a row lock at save (P1.14). Two branches with one GSTIN must still never print the same number in a year, so each branch's number carries its code once the business has a second branch: `ABC/AND/2026-27/001`, `ABC/THN/2026-27/001`. A business with one branch keeps the format the owner set (#8) with no code. P1.6 only adds `code`; P1.14 builds the counter and the format.

## 7. API

All under `settings.manage` (owner only) unless noted. Written in the P1.4/P1.5 style (`ZodBodyPipe`, error codes the web app translates).

| Route | Owner's password? | Does |
| --- | --- | --- |
| `GET /api/branches?includeArchived=` | no | Every branch: id, code, name, address, state, GSTIN, licences, head office or not, archived or not, how many computers and staff call it home. Also `session.own` gets a short list (id, code, name) for the picker. |
| `POST /api/branches` | no | Adds a branch. `409 code_taken`. Logs `branch.created`. |
| `PUT /api/branches/:id` | no | Edits it. Same rules as the business details card today (bills already printed keep their details, #11). |
| `POST /api/branches/:id/archive` | yes | Refused for the head office, and while active staff have it as their home branch (`409 branch_in_use`, with the count: move them first). Ends sessions on its computers and forgets the computers. Stock and history stay. |
| `POST /api/branches/:id/restore` | no | Brings it back. |
| `PUT /api/devices/:id/branch` | yes | Moves a remembered computer to another branch; ends its sessions. |
| `PUT /api/staff/:id/branches` (`staff.manage`) | yes (it gives access, P1.5 question 3) | The extra branches a staff login may work at. |
| Owner's first login on a new computer | | With 2+ active branches, the login answers `choose_branch` with the list, and the login is sent again with `branchId`. With one branch, nothing changes. |
| Staff login | | Refused with `wrong_branch` ("Ramesh can't log in at Thane") when the computer's branch is neither their home nor an allowed branch. Checked on every request too, with the permissions (ADR 0044), so removing a branch reaches a logged-in cashier on the next click. |
| Read routes that show branch data | | Take `?branch=<id>` (owner: any; staff: ignored, always their session's) and `?branch=all` where combining makes sense. |

The session view gains `branch` (id, code, name of the computer's branch) and, for the owner, `branchCount`, so screens can hide branch things when there is one.

## 8. Screens

All text in English, Hindi and Hinglish. Native `<dialog>`s.

| Screen | Who | What |
| --- | --- | --- |
| **Settings → Branches** | owner | A card listing branches (code, name, city, GSTIN, computers, staff), an Add branch button, Edit, Archive (with what it does), "Show archived". The business-details card keeps the business-wide fields; branch fields move to the branch's own form. |
| **Settings → Remembered computers** | owner | Each computer shows its branch, with a "Move to another branch" action (owner's password). |
| **Branch picker** (top bar) | owner, only with 2+ branches | Shows the branch the page is showing. Lists branches and, on pages that can combine, All branches. Remembered per tab. The computer's own branch is marked "this counter". |
| **Choose branch** (first owner login on a new computer, 2+ branches) | owner | A list of branches; the choice is the computer's branch until moved. |
| **Staff edit** (P1.5 screen) | owner | Home branch picker and "Can also work at" checkboxes, only with 2+ branches. |
| **Every page** | everyone | The branch name sits beside the business name in the sidebar when the business has 2+ branches, so a cashier always sees where they are. |

## 9. Questions for the owner

**Answered 2026-11-22:** the owner took all seven recommendations (1A to 7A). They are `00` #54–#60.

Each has a recommended answer. None changes a DECIDED point.

1. **Which branch a person is working in** (section 4).
   - A. The computer decides; everything done on it belongs to its branch. The owner's picker only changes what pages **show**, including All branches. **Recommended:** a bill always carries the address and invoice number of the shop it was made in, and nobody can save something at the wrong branch by forgetting a picker.
   - B. The owner's picker switches the branch for everything, billing included.
   - C. A branch box on every form that saves something.

2. **A new computer when the business has several branches.**
   - A. The owner's first login on it asks which branch it is in. **Recommended:** it is asked once, when the owner is there to answer.
   - B. It goes to the head office; the owner moves it in Settings if needed.

3. **Moving a computer to another branch.**
   - A. In Settings, with the owner's password; it logs out whoever is on that computer. **Recommended:** it decides where bills and stock go, so it is as sensitive as a permission.
   - B. No password; just a confirmation.

4. **Staff and other branches** (`00` #35).
   - A. The owner ticks the extra branches per staff login. They can log in only on computers at their home or a ticked branch, and see only the branch they are logged in at (no picker for staff). **Recommended:** it is what #35 says, and it keeps each branch's data to the people working there.
   - B. As A, but staff with extra branches also get the picker to look at those branches from any counter.

5. **Invoice numbers with several branches** (section 6).
   - A. Each branch has its own series, with its short code in the number (`ABC/AND/2026-27/001`). A business with one branch keeps its format unchanged. **Recommended:** counters in two shops can bill at the same moment without waiting on each other, and every number is still unique.
   - B. One series for the whole business, shared by all branches.

6. **Archiving a branch.**
   - A. Allowed for any branch except the head office, once no active staff have it as their home branch (move them first). Its computers are logged out and forgotten; its stock and history stay readable; it can be brought back. **Recommended:** nothing is lost, and nothing is left pointing at a closed shop.
   - B. Also refused while the branch still holds stock (the owner must transfer or write it off first; transfers come in P1.11).

7. **A business with one branch.**
   - A. Sees nothing about branches (no picker, no branch column, no code in invoice numbers) until it adds a second; Settings shows a single "Add a branch" button. **Recommended:** most shops have one branch, and `01` #13 already chose this for transfers.
   - B. Always shows the branch name and picker.
