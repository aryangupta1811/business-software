# P1.1 Tenancy & Data Safety — Design Spec

**Status:** approved section by section by the owner on 2026-11-01 (sessions 11–12); this file awaits the owner's review before the implementation plan is written.
**Task:** P1.1 in `docs/PROGRESS.md`. **Related ADRs:** 0001 (UUIDs made at the source), 0006 (shared tables + RLS), 0007 (data safety in the database), 0019 (roles, default privileges). New ADR: 0027 (tenancy implementation: UUIDv7, the policy helper, the guard test).

## 1. Goal and success criteria

The first real tables, and the rule every later business table follows, so no module can see or write another business's rows even when its code is wrong.

Done means:
- `businesses` and `branches` tables with Row-Level Security, `FORCE`d;
- one way for code to run a transaction for a business (`withBusiness`), with the business set transaction-locally;
- a guard test that fails if any table lacks `business_id`, RLS, `FORCE` or a correct policy, gives `app_runtime` more than SELECT/INSERT/UPDATE, or has a `branch_id` without the composite foreign key;
- integration tests that try to read and write across businesses and must fail; no business set means no rows.

## 3. Database objects (migration `0001`) — approved

**Tables:**

```
businesses  id uuid PK default uuidv7() · name text not null · created_at timestamptz not null default now()
branches    id uuid PK default uuidv7() · business_id uuid not null → businesses(id)
            · name text not null · created_at timestamptz not null default now()
            · unique (business_id, id)
```

- `unique (business_id, id)` on branches lets later branch-level tables (stock…) reference `(business_id, branch_id) → branches(business_id, id)`, so the database refuses a row of business A pointing at a branch of business B. RLS alone wouldn't catch that.
- Indexes start with `business_id` (ADR 0006). The `unique (business_id, id)` index also serves `branches.business_id` lookups, so no other index is needed now.

**Function `app_current_business_id()`:** reads `current_setting('app.business_id', true)`, turns missing *or empty* into NULL (`nullif(…, '')::uuid`), returns uuid. Plain SQL, `STABLE`, **not** `SECURITY DEFINER`, so it runs with the caller's rights.

**Policies:** `businesses`: `id = (select app_current_business_id())`; `branches` and every future tenant table: `business_id = (select app_current_business_id())`. One policy for all commands, the same expression in `USING` and `WITH CHECK`, so you can neither insert another business's row nor move a row to another business. The `(select …)` wrapper makes PostgreSQL evaluate it once per query (an InitPlan), not per row. Policies apply to PUBLIC (with `FORCE`, the owner is filtered too).

**`FORCE ROW LEVEL SECURITY`** on both tables: owners otherwise skip RLS silently.

**Grants:** unchanged; P0.3's default privileges give `app_runtime` SELECT, INSERT, UPDATE and never DELETE.

**Migration form:** Drizzle generates the tables and policies from `schema.ts`; the function and the `FORCE` lines are added by hand to the same migration, with the function before the policies that call it. To check while implementing: editing the generated file vs `drizzle-kit generate --custom`; Drizzle can't generate `FORCE` (checked: drizzle-kit 0.31 knows `ENABLE ROW LEVEL SECURITY` only).

## 4. Code: how the app uses tenancy (`packages/db`) — approved

**Schema helper** (`src/tenancy.ts`): `businessId()` (uuid, not null, references `businesses(id)`), `createdAt()`, and `tenantPolicy(column)`, which returns `pgPolicy('tenant_isolation', { for: 'all', using, withCheck })` with the same check in both. Every tenant table uses the same policy name, so the guard test can find it. Example:

```ts
export const branches = pgTable('branches', {
  id: uuid('id').primaryKey().default(sql`uuidv7()`),
  businessId: businessId(),
  name: text('name').notNull(),
  createdAt: createdAt(),
}, (t) => [tenantPolicy(t.businessId), unique().on(t.businessId, t.id)]);
```

**`withBusiness(db, businessId, work)`**, the only way code reads or writes tenant data: opens a Drizzle transaction, runs `select set_config('app.business_id', $1::uuid::text, true)`, then `work(tx)`; commits, or rolls back if `work` throws. The `::uuid` cast refuses a malformed ID at once (`22P02`) instead of at the first query. `true` = transaction-local, so a pooled connection can't carry the business into the next request.

**`withNewBusiness(db, work)`**, for signup: `select uuidv7()`, sets it as the current business, calls `work(tx, businessId)`; the caller inserts the `businesses` row with that ID and the policy's check passes. P1.3 adds the first branch and the owner's login in the same transaction. No bypass role.

**Outside these two functions** a tenant table shows no rows and refuses inserts: a forgotten wrapper fails safe. Health checks (`select 1`) don't touch tenant tables.

**Exports** from `@business-software/db`: the tables, `withBusiness`, `withNewBusiness`, a `Transaction` type. No API code changes in P1.1.

**Left for later:**
- **P1.4 login:** at login the username is known but the business isn't. Needs a narrow lookup, probably a `SECURITY DEFINER` function returning only the matching user's ID, business and password hash, with PUBLIC's EXECUTE revoked. P1.4 decides.
- **P2.7 jobs:** the worker calls `withBusiness` per job, with the business stored in the job.

## 5. Tests — approved

Integration tests on a throwaway PostgreSQL (Testcontainers, ADR 0013), written before the code (TDD).

**A. Guard test** (`src/tenancy-guard.test.ts`): a catalogue query (`pg_class`, `pg_policy`, `information_schema`, `pg_constraint`) lists every table in schema `public` that breaks a rule:

1. RLS not enabled, or not `FORCE`d.
2. No policy named `tenant_isolation`, or it is wrong: it must be permissive, for all commands (`*`), to PUBLIC, with the same expression in `USING` and `WITH CHECK`, calling `app_current_business_id()`.
3. No `business_id uuid not null` column (`businesses` itself is the only exception).
4. `app_runtime` holds a table privilege outside {SELECT, INSERT, UPDATE} (DELETE, TRUNCATE, TRIGGER, REFERENCES). Fewer is fine, so P1.2's insert-only log passes.
5. A `branch_id` column without a composite foreign key `(business_id, branch_id) → branches(business_id, id)`.

*Added after the final review (ADR 0027):* rule 2 also fails on any extra permissive policy (permissive policies are ORed, so one `using (true)` shows every business); `tenant_fk`: every foreign key into a tenant table other than `businesses` pairs `business_id` with `business_id` (foreign-key checks skip RLS); `kind`: no materialized views or foreign tables in `public` (RLS never applies to them).

Proving the guard: it first runs on the real schema and must report **nothing**; then the test creates one deliberately broken probe table per rule (as `app_owner`) and expects each to be reported with the right rule; then it drops them. No exceptions list today; a future non-tenant table needs an entry with its reason beside it.

**B. Behaviour tests** (`src/tenancy.test.ts`): businesses A and B, each with a branch, created as `app_runtime` through `withNewBusiness`.

1. Inside A: only A's business and A's branches are visible.
2. Read across: inside B, A's branches are invisible; updating one changes 0 rows.
3. Write across: inside B, inserting a branch with A's `business_id` → `42501`; moving B's branch to A → `42501`.
4. Nothing set: select returns no rows; insert → `42501`.
5. Pooled connection (`max: 1`): after `withBusiness(A)` commits, a plain query on the same connection returns 0 rows and no error; the same after a `withBusiness` whose `work` throws (rollback).
6. Malformed ID: `withBusiness(db, 'not-a-uuid', …)` → `22P02`, and `work` is never called.
7. `FORCE`: the owner role with no business set sees 0 rows.
8. Signup: `withNewBusiness` creates a business visible inside its own ID only; the ID is a version-7 UUID.
9. Delete: deleting from `businesses` or `branches` → `42501` (a real attempt, besides the guard's catalogue check).

**Unchanged:** `src/roles.test.ts` (P0.3). `pnpm check` and the five CI checks green before the PR.

## Known gotchas (found in brainstorming)

- After a transaction-local `set_config` ends, the setting reads back as `''`, not NULL, on that connection; `''::uuid` throws. Handled by `nullif`.
- Signup is a chicken-and-egg: no business can be inserted before one is set. Handled by setting the new ID first.
