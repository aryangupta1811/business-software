## 1. Goal and success criteria

A cashier can build a bill with the keyboard and the scanner alone: scan or search items, change quantities, give discounts within their limit (or with the owner's password), attach a customer, take payment in one or several modes, and hold a bill to serve the next customer. Every number on screen comes from `calculateBill` (P1.12). P1.13 ends where the bill is handed to the server; **P1.14 saves it** (invoice number, stock, the atomic transaction).

Done when:

1. A scanned barcode puts the item on the bill in **under 200 ms**, measured in Chrome with 5,000 items in the catalogue, with no request to the server on the way.
2. The screen's totals equal `calculateBill`'s for the same cart, always. There is no second copy of the GST maths.
3. Every bill action has a key. A full bill (scan, quantity, discount, customer, split payment) can be made without touching the mouse.
4. A discount above the cashier's limit can't reach the save request without an owner approval, and the server re-checks it at save (P1.14).
5. A held bill can be resumed on any counter of the branch. It doesn't touch stock. Prices changed while it waited are shown.
6. The catalogue copy picks up an item edited on another computer within about a minute, including an edit whose transaction committed late (section 4).
7. The owner's lock screen and a dropped connection never lose the bill on screen (`00` #38, ADR 0001).
8. Three languages, light and dark, 1024 px, no CSP violations.

## 3. The screen and the keyboard flow

**Layout at 1024 px** (one page, `/bill`, in the sidebar as "Billing" with `Alt+B`):

│ [ Search or scan  (F2) ...................................... ]  Retail ▾ (F8)    │
│ ┌ results (only while typing) ┐                                                   │
│ # │ Item                 │ Qty      │ Price   │ Disc. │ Amount │                    │
│ 1 │ Tata Salt 1 kg       │ 2 piece  │  28.00  │       │  56.00 │                    │
│ 2 │ Basmati rice (loose) │ 0.750 kg │ 120.00  │ 5%    │  85.50 │  ← selected        │
│ …                                                                                 │
├───────────────────────────────────────────────┬───────────────────────────────────┤
│ Customer (F3): walk-in                         │ Items 2 · Gross 146.00            │

**The search box always has the focus** unless a dialog is open. Typing filters the catalogue copy; Enter adds the highlighted result. A scanner's burst (`ScanBuffer`, P1.7) adds the item straight away, even while the results list is open.

**Quantity:**
- `3*` typed before a scan or search sets that line's quantity to 3 (a common point-of-sale habit, and it keeps the cashier on one box).
- For a loose item (`kg`, `g`, `litre`, `ml`, `metre`, `foot`), adding it moves the focus to the quantity box with the unit shown; Enter goes back to search.
- `F4` edits the selected line's quantity. `+` and `−` on the selected line (from the list, not the search box) change it by one unit.
- Whole units for `piece`, `pair`, `dozen`, `box`, `pack`, `bag` (`checkStockQuantity`, P1.8).

**Proposed keys** (question 1). All through `useShortcut` (ADR 0026); they work while the search box has focus because F-keys and `Ctrl`/`Alt` combos are allowed in fields:

| Key | Does |
| --- | --- |
| `F2` | Focus the search box |
| `F3` | Customer box (find by phone, or add) |
| `F4` | Quantity of the selected line |
| `F6` | Discount on the selected line |
| `F7` | Discount on the whole bill |
| `F8` | Retail / wholesale price (only with the `wholesale_price` feature) |
| `F9` | Hold this bill / open held bills |
| `F10` | Payment panel |
| `↑` `↓` | Move the selected line (from the search box when it's empty) |
| `Ctrl+Delete` | Remove the selected line |
| `Alt+N` | New bill (asks first if the bill isn't empty, question 7). Same key as "New item" on the Items page; each is registered only while its page is open |

| `?` | The shortcut list (exists) |

`F1`, `F3`, `F6`, `F7` and `F10` all have a meaning in Chrome (help, find, address bar, caret browsing, menu). The registry already calls `preventDefault` for a matching shortcut; section 12 closes the gaps the P0.7 review found (held keys, open dialogs).

**Unknown code scanned** (question 8): "No item with code 8901234567890". With `items.manage`, Enter opens a short "Add item" dialog (name, price, GST rate, HSN, unit) and the item lands on the bill when saved. An archived item's code says so and offers nothing (restoring is on the Items page).

**Nothing pops up while billing** (sitting 2, `07` A5): alerts stay behind the bell.

## 4. The catalogue copy in the browser

**Why a copy:** NFR 5 wants a scan on the bill in under 200 ms. The server is now in Mumbai (about 0.06 s per round trip from India, ADR 0033), but a shop's 4G or broadband adds jitter and the odd slow second, and a counter scans dozens of items a minute. A lookup in memory takes well under a millisecond, whatever the network does. The server still decides at save: it re-prices every line from the database (section 10), so a stale copy can never make a wrong bill, only a "prices changed" prompt.

**What's in it** (for the caller's business, at the caller's branch):

- Live items: id, kind, name, Hindi name, code, stock unit, selling and wholesale price, MRP, price-includes-tax, GST rate, HSN, `version`.
- Their live packs (unit, size, own price and MRP, sold as pack) and live barcodes (code, pack).
- Archived items as a slim entry (id, name, `archived: true`, barcodes) so a scan can say "archived".
- **Not** the purchase price, ever (the counter doesn't need it, and it would sit in the browser of a shared computer).
- **Stock at the caller's branch**, only with `stock.view` (quantity and low-stock level), so a line can show "2 left" and warn before the save does. Without `stock.view` the screen shows no numbers and the warning comes from the save (P1.14).

**Size:** about 300 bytes an item as JSON; 5,000 items is about 1.5 MB, about 200 KB after Caddy's `encode zstd gzip` (already on). Loaded once when the billing page opens.

**Staying fresh:**

```
GET /api/billing/catalogue                     → { items, stock, serverTime }
GET /api/billing/catalogue?since=<serverTime − 60 s> → only what changed since then
```

- Every 60 s while the page is open, when the tab comes back into view, and after any "prices changed" answer from the save.
- **The overlap (the subtle part):** `items.updated_at` is set when the change is *made*, but other counters only see it when its transaction *commits*, which can be seconds later. A sync that asked for "changed since my last `serverTime`" would miss a change made just before that time and committed just after it. So each sync asks for "changed since 60 s before my last `serverTime`", which is longer than any transaction can stay open (`statement_timeout` 10 s and `idle_in_transaction_session_timeout` 15 s, ADR 0041). Rows seen twice are simply replaced (by id; `version` decides which copy is newer).
- Stock comes from `item_stock.updated_at` the same way.
- A full reload every 30 minutes as a safety net, so a missed row heals itself.
- Everything the copy depends on already bumps `items.updated_at`: item saves, archive and restore, barcodes added and removed, own units renamed or archived (P1.7). A test pins that list so a future change can't skip it.

**Search** in memory: case and accents ignored; matches the English name, the Hindi name and the item code. Ranked: exact code, then name starts with, then a word starts with, then contains. Top 20 shown. Transliteration ("aata" finding "आटा") is not in v1 (`ideas-backlog.md`).

**Kept in memory only** (not IndexedDB): the copy is rebuilt each time the page opens, so nothing stays on a shared computer after Chrome closes (`00` #40).

## 5. The cart

A line is: `itemId`, `packId` (null = the stock unit), `quantityThousandths` (of the pack, or of the stock unit), `unitPricePaise` (as shown), `discount?`, and room for `batchId` and `serials` (P1.10). Rules:

- **Price** comes from the copy: the pack's own price, or `size × price` (`packPrice`, P1.7); wholesale price when the bill is in wholesale mode and the item has one, else retail (question 10). **No typed prices** at the counter (question 3): a lower price is a discount, so it goes through the limit and the log. Because the item's own prices are already at or below MRP (P1.7 checks), the counter can never go above MRP.
- **The same item and pack scanned again adds to its line** (question 2), unless that line has a discount, in which case a new line starts so the discount isn't silently applied to more units.
- **Services** can be billed (repairs, `00` business-type table); they never show stock.
- **A regular business can't add an item with no GST rate or HSN** (`02` #21, #24; `calculateBill` throws for a missing HSN on a tax invoice). The cashier sees "Set the GST rate for this item first"; with `items.manage`, Enter opens the item's GST fields in a dialog.
- **Totals:** every change calls `calculateBill` with the business's scheme, the branch's state, the place of supply (section 7), the lines and the bill discount. The screen shows exactly its result.
- **Stock warning** (with `stock.view`): a line that would take the branch's stock below zero shows "Only 2 in stock" in the warning colour. Under `block` the line shows it too, and the save will refuse (P1.14). No dialog: the cashier sees it and carries on.
- **The open bill survives:** the lock screen (it's an overlay, `00` #38), a lost connection (ADR 0001: "offline" badge, bill kept), and a reload (the open bill is kept in `sessionStorage` for that user and cleared at logout, so Chrome closing removes it, `00` #40).

## 6. Discounts and the owner's approval

**Kinds** (`02` #5): per line and per bill, each a percent or an amount. GST is worked out after both (the engine). A rupee bill discount means the customer pays exactly that much less (the engine's rule from 2026-11-18).

**The staff limit** (`02` #12, question 4). The owner has no limit. A staff login has `discount` switched on or off and a maximum percent (P1.5 stores both; until P1.5 a staff login's limit is 0). A bill is within the limit when:

1. each line's own discount is at most the limit, as a percent of that line's gross; **and**
2. the whole bill's discount (gross − total) is at most the limit, as a percent of the bill's gross.

One shared function, `discountWithinLimit(bill, limitBasisPoints)`, used by the screen and by P1.14's save.

**Above the limit** (question 5): the screen marks the bill "Needs owner's OK" and opens a native `<dialog>` with a password box. The owner types their password at the counter. The server checks it (`requireOwnerPassword`, P1.4, under its rate limit) and stores an **approval**:

- for this bill only (its `billKey`), up to the discounts shown when it was given (line maximum and bill total, in basis points);
- one use, gone after 30 minutes, used up by the save (P1.14);
- logged at once as `discount.approved` (reason optional), with the approving owner, the percentages and the bill key.

If the cashier then raises a discount past what was approved, the bill needs a new OK. The password never sits in the browser: it goes once to the approval call and is dropped.

**Logging:** `02` #12 says every discount is in the entry log. The approval is logged when given; the discounts themselves are logged with the bill when P1.14 saves it (the `bill.created` entry carries them), so a discount on a bill that never got saved leaves no log row except an approval. P2.6's "watched actions" filter includes both.

## 7. Customers

**Capture** (`02` #2, #7; `03` #1): `F3` opens a box. Typing 10 digits finds a customer by phone; none found → add one with a name (and the phone already typed). A walk-in bill needs nothing.

**B2B:** a "Business customer" tick asks for GSTIN (checked with `isValidGstin`), the legal name and an address. The state comes from the GSTIN's first two digits.

**Place of supply** (`02` #3, question 9): the branch's own state by default, so a counter sale is CGST + SGST. For a B2B customer from another state, the default is the customer's state (IGST), and the cashier can switch it back to "delivered at the counter" (the branch's state). A B2C bill can also pick another state ("sent to …"). The screen shows the tax type next to the total so the switch is visible.

**Rule 46:** an unregistered buyer's name and address (with state) are needed on a tax invoice of ₹50,000 or more. The screen asks for them when the total crosses that; the save re-checks.

**Data:** a new `customers` table now (section 11), so udhaar (P1.18) only adds columns.

## 8. Payment

`F10` opens the payment panel:

- Modes: **cash, UPI, card, cheque** (`02` #10). Udhaar joins with P1.18 (`03` #1, #9, #10 need its ledger, credit limit and switch).
- **Split** (`02` #11): add rows until the paid total equals the bill total. `Tab` moves between rows; each mode has a number key (`1` cash, `2` UPI, `3` card, `4` cheque) inside the panel.
- **Cash:** the cashier types what the customer handed over and the panel shows the change. Only cash can be more than what's left to pay.
- **References:** optional for UPI and card (last digits or UTR), required for cheque (its number).
- **Enter** on a paid bill sends it to the save (P1.14). Until P1.14 merges, the panel stops at "Ready to save".

## 9. Held bills

`02` #8: "a counter can hold several open bills, serve the next customer and bring a held bill back. A held bill doesn't touch stock until it is saved."

**Where they live** (question 6): on the server, per branch, in a `held_bills` table, so any counter of the branch can bring one back, and a crash or a closed Chrome doesn't lose it.

- `F9` holds the open bill (an optional short label, e.g. "blue shirt uncle") and starts a new one. `F9` on an empty bill lists the branch's held bills, newest first, with label, items, total, who held it and when.
- **Resume:** the bill comes back onto the screen and the held row is closed (`resumed_at`, by whom). Lines are re-priced from the current copy; any changed price is highlighted for the cashier.
- **Discard** (question 7): a held bill is never deleted; it's closed with `discarded_at` and logged as `bill.draft_discarded` with its lines and total. Clearing a non-empty open bill with `Alt+N` writes the same entry.
- The approval (section 6) stays with the bill's key, so a resumed bill keeps its owner's OK if it is still within 30 minutes.

## 10. What P1.13 hands to P1.14

P1.13 writes the request schema; P1.14 implements `POST /api/bills` against it.

```ts
billDraftSchema = {
  billKey: uuid,                     // idempotency key, made when the bill is started (ADR 0007)
  priceList: 'retail' | 'wholesale',
  customerId: uuid | null,
  placeOfSupplyStateCode: string,
  lines: [{ itemId, packId | null, quantityThousandths, shownUnitPricePaise, discount? }],
  billDiscount?: Discount,
  payments: [{ mode: 'cash' | 'upi' | 'card' | 'cheque', amountPaise, tenderedPaise?, reference? }],
  approvalId?: uuid,
  heldBillId?: uuid,
  shownGrandTotalPaise: number,
}
```

The server (P1.14) re-reads every item and price inside the save's transaction, runs `calculateBill` and `discountWithinLimit` itself, and compares. A different price or total answers `409 prices_changed` with the new prices; the screen syncs, highlights the lines and asks the cashier to confirm. **The browser's numbers are never trusted.**

## 12. Shortcut module changes (P0.7 review minors, listed under P1.13)

1. `preventDefault` a matching key even when it is ignored for auto-repeat or an open dialog (except `Esc`), so a held `F3` or `F10` doesn't reach Chrome.
2. Reserve `F5`, `F11`, `F12` with any modifier, `Ctrl+Shift+T/W/N/R`, `Ctrl+F4` and `Alt+F4`.
3. A clash throws only in development (`import.meta.env.DEV`) and in tests; in production it logs and keeps the first.
4. Pause shortcuts whenever any `dialog:modal` is open, not only the help panel; each billing dialog registers its own keys while open.
5. Ignore an event already `defaultPrevented` by a field (the decision the review asked for).
6. Scanner input with no field focused goes to the search box (the billing page listens on `window` through `ScanBuffer`).

## 13. GST rate 1.5% (checked 2026-11-20)

The P1.7 design left 1.5% out because only secondary sources mentioned it. Checked now:

- **Notification 9/2025-Integrated Tax (Rate), 17 Sept 2025, in force from 22 Sept 2025** sets IGST at **1.50% for goods in its Schedule VI**, and 0.25% for Schedule V. The Central Tax (Rate) version of the same notification sets **0.75%** CGST for Schedule VI, so CGST 0.75% + SGST 0.75% = 1.5%.
- Schedule VI holds HSN 7102 goods other than rough diamonds (Schedule V), i.e. **cut and polished diamonds**. The earlier doubt ("1.5% is just the CGST half of 3%") is answered: 3% (gold, silver, jewellery) is a different schedule, and 1.5% is a full rate in its own right.
- The copy read is marked as amended by Notifications 19/2025 (31 Dec 2025) and 1/2026 (30 Apr 2026). Not checked whether either touches Schedule VI.
- Sources: CBIC's copy of Notification 9/2025-IT(Rate) (courier.cbic.gov.in), the ICAI Navi Mumbai branch's copy, taxcode.in's copies of 9/2025-CT(Rate) and -IT(Rate).

**Recommended (question 12):** add `150` to `GST_RATES` in PR 1, with the regenerated check constraint. The engine already splits 1.5% into two 0.75% halves correctly (it halves by dividing by `2 × base`, so odd basis points are fine; a test with 150 is added). A jeweller is not one of the five business types, so this is about correctness of the list, not a feature.

## 15. Tests (test-first for every rule)

**`packages/shared` (unit):**
- `discountWithinLimit`: line limit, bill total limit, rupee discounts converted, the owner's null limit, exactly at the limit, one paisa over.
- Cart → `BillInput`: packs (`size × price` and own price), wholesale fallback to retail, merging the same item, a discounted line not merged, quantity prefix `3*`.
- `billDraftSchema`: unknown fields refused, payments must add up, cash only may exceed, cheque needs a reference.
- Search ranking: code, prefix, word prefix, contains, Hindi name.
- `GST_RATES` includes 150; `calculateBill` with 150 bp, CGST+SGST and IGST, inclusive and exclusive.

**`packages/db` (Testcontainers):** the three tables pass every guard rule (`backup_read`, `FORCE`, composite keys, no `DELETE`); a held bill can't be both resumed and discarded; cross-business: B can't resume A's held bill or use A's approval; customer phone and GSTIN unique within a business only; the regenerated rate check accepts 150.

**`apps/api`:**
- Catalogue: full and `since`; no purchase price, ever; stock only with `stock.view`; archived items slim; **a change committed after the previous `serverTime` but stamped before it is returned by the next sync** (the overlap, with a held-open transaction).
- Held bills: hold, list, resume once (a second resume is `409`), discard logs, another branch's held bill is `404`.
- Approvals: wrong password `403` under the rate limit, right one stores and logs, expires after 30 minutes (injected clock), owner and staff callers.
- Customers: find, add, edit with `version`, invalid GSTIN, phone normalised, logged.
- Permissions on every route; route census (ADR 0036).

**`apps/web`:**
- The whole keyboard flow in one test: scan, `3*` scan, `F4`, `F6` over the limit → approval dialog, `F3` add customer, `F10` split payment, `F9` hold and resume.
- Totals on screen equal `calculateBill`'s.
- Shortcut fixes (section 12), each with a test.
- Lock screen over a bill, then unlock: the bill is still there.
- **Speed:** with 5,000 items, scan to line drawn under 200 ms (measured in Chrome's Performance panel in the real-app check; a unit test keeps lookup under 5 ms).

   - A. Adds 1 to its line (a new line only if that line has a discount). **Recommended:** a short bill is easier to check and print.

   - A. Not allowed; a lower price is given as a discount. **Recommended:** every reduction then goes through the staff limit and the log (`02` #12), and nothing can go above MRP.

   - A. Each line's discount and the whole bill's total discount, each as a percent, must be within the limit. **Recommended:** stops both "50% off one costly item" and "10% off everything".

   - A. When the discount is given; the OK covers that bill only, up to the discounts shown, for 30 minutes. **Recommended:** the owner is usually standing there at that moment, and the cashier knows before the customer pays.

   - A. On the server, per branch: any counter of the branch can bring one back, and a crash doesn't lose it. **Recommended.**
