## 1. Goal and success criteria

The owner can give each cashier a login of their own, choose exactly what that person may do, and take it away again, and the server enforces it on every request.

Done when:

1. The owner adds a staff login (name, username, password, home branch) and that person logs in on a counter with the permissions the owner chose. A new login gets the defaults of section 4.
2. Every switch changes what the server allows: a route a staff member doesn't hold answers `403 forbidden`, whatever the screen shows.
3. A permission change reaches a staff member who is **already logged in** on their next request, with no new login (section 5).
4. Changing permissions, the discount limit, a password, or reactivating a login asks for the owner's password (question 3). A wrong password changes nothing, and it counts against the owner-password rate limit.
5. Deactivating a login ends its sessions at once; its history stays; reactivating brings it back. Nothing is deleted.
6. Every change is in the entry log with who did it, the old values and the new values. No log row ever holds a password.
7. Staff can't see or open owner-only screens (Settings, Staff). The sidebar shows only what the person may use.
8. A staff member can change their own password on a screen they can open (Module 00 #46).
9. Owner and staff of one business never see another business's staff (a test over two businesses).

## 2. What P1.5 does and doesn't do

| In P1.5 | Left for |
| --- | --- |
| Create a staff **login**; edit name, username, home branch | Staff records (phone, joining date, salary, weekly off, overtime) and staff **without** a login (Module 00 #19): **P2.3** |
| Per-person switches for every permission that exists today, the discount limit | Switches for later modules' features: each module adds its own (section 4, last table) |
| Reset a staff password, deactivate, reactivate (buttons and routes) | The final settlement slip when someone leaves (`05` #4): **P2.3** |
| Home branch stored on every staff login (`home_branch_id`) | Adding branches, the branch switcher, letting a login work in other branches, the login check against the computer's branch: **P1.6** |
| Live permissions in the session, the session view's `permissions` and `discountLimitBasisPoints`, nav and route hiding | The entry-log viewer and its "watched actions" filter: **P2.6** (it will include `staff.permissions_changed`) |
| A password screen every login can open | Forcing a new password at first login: ideas backlog (question 7) |

Today a staff session holds only `session.own` (`callerOf` in `session.service.ts`). P1.4's design said it would build the owner-sets-password and deactivate services; the code has only `setPasswordIn` and the `deactivated_at` check, so P1.5 builds both completely.

## 3. Data

No new table. A staff login is a row in `users` (`role = 'staff'`), which already holds `username`, `password_hash`, `deactivated_at` and `password_changed_at`. Staff without a login (`#19`, P2.3) will be the same table with no password, so P2.3 adds columns, not a second identity.

### New columns on `users` (one migration, `0013` unless another lands first)

| Column | Type | Rule |
| --- | --- | --- |
| `home_branch_id` | uuid, null | `#35`. Composite key `(business_id, home_branch_id) → branches(business_id, id)` (ADR 0027). `check (role <> 'staff' or home_branch_id is not null)`. Null for the owner. |
| `permissions_added` | text[], not null, default `{}` | Staff switches the owner turned **on** beyond the defaults. |
| `permissions_removed` | text[], not null, default `{}` | Staff switches the owner turned **off** from the defaults. `check (not (permissions_added && permissions_removed))`. |
| `discount_limit_basis_points` | integer, null | `02` #12: the most this login may discount alone. `check (between 0 and 10000)`. Basis points like every rate (ADR 0008). Null means the switch was never set. |
| (existing) `check` | | `check (role <> 'staff' or password_hash is null or username is not null)`: a login always has a username (the P1.4 design planned it; the schema lacks it). |
| (owner rows) | | `check (role <> 'owner' or (cardinality(permissions_added) = 0 and cardinality(permissions_removed) = 0 and discount_limit_basis_points is null))`: the owner holds everything by role, so these stay empty. |

The users table already has `unique (business_id, id)` and `unique (business_id, username)`, so the tenancy guard test needs nothing new: no new table, and the one new key follows the composite rule.

### Why "changes from the defaults", not the full list

Every later module adds permissions. If we stored each person's full list, a permission that is **on** by default (for example `03` #11, recording payments, is for all staff) would be missing for every login made before that module. A migration can't fix it: the migration role sees no `users` rows under row-level security (ADR 0027's trap). Storing only the differences means a new permission takes its default for everyone who never had a choice about it, and a sensitive one is simply off until the owner turns it on.

```
effective = ((defaults ∪ added) − removed) ∩ switchable, then drop any switch whose parent is off, plus session.own
```

- **Names aren't checked by the database.** The list grows with every module, and a check on it would need a migration each time (as the 1.5% GST rate did). Zod checks the names on the way in. A stored name the code doesn't know, or one that is owner-only, is ignored when read, so a bad value can never grant anything. A test proves it.
- **The discount limit.** Effective limit = the `billing.discount` switch on ? `discount_limit_basis_points` (null counts as 0) : 0. That is the value the session view calls `discountLimitBasisPoints` (null for the owner).
- **Archive, never delete.** `deactivated_at` already exists. A deactivated login keeps its username (nobody else can take it; reactivating gets it back, `#34`) and its rows in every table.
- **Concurrency.** One owner edits staff, rarely, so saves are last-write-wins with no `version` column. The log keeps both values, so nothing is silently lost.

### Entry log (ADR 0028), new `ENTRY_ACTIONS`

`entityType` is `user`, `entityId` is the staff member's id, `actorId` is the owner. None needs a reason, except that deactivating accepts an optional one.

| Action | When | `before` → `after` |
| --- | --- | --- |
| `staff.created` | login added | — → name, username, home branch, effective permissions, discount limit |
| `staff.updated` | name, username or home branch changed | the changed fields only |
| `staff.permissions_changed` | switches or limit saved (only if something changed) | effective permission list and limit, before and after |
| `staff.deactivated` | login switched off (its sessions end in the same transaction) | — |
| `staff.reactivated` | login switched on again | — |
| `user.password_reset` (exists) | owner sets a staff password | `after.via` gains the value `owner` |

`user.logged_out` already records `after.cause: 'deactivated'` for each ended session. A save that changes nothing writes no row.

## 4. Permissions

`PERMISSIONS` stays the list of everything a route can require. P1.5 adds one file's worth of shared code next to it: `STAFF_SWITCHES`, the owner's switch list. Each entry has the permission, its group on the screen, its default for a new login, and its parent switch if it needs one. A later module adds its permission to both lists in the same PR.

### Existing permissions

| Permission | What it opens | Owner can switch on for staff? | Default for a new staff login | Needs |
| --- | --- | --- | --- | --- |
| `session.own` | own session: lock, log out, change own password | always on, no switch | on | |
| `settings.view`, `settings.manage` | Settings, remembered computers, recovery key | **no, owner only** (question 4) | off | |
| `staff.manage` (new) | the Staff page and its routes | **no, owner only** | off | |
| `items.view` | Items list and item page (never the purchase price) | yes | **on** | |
| `items.manage` | add, edit, archive items, categories, units | yes | off | `items.view` |
| `items.view_cost` | the purchase price, margin (`01` #1, `00` #16) | yes | off | `items.view` |
| `stock.view` | stock levels and history; stock beside items at billing | yes | **on** | |
| `stock.adjust` | opening stock and adjustments (`01` #11) | yes | off | `stock.view` |
| `billing.sell` | the billing page, held bills | yes | **on** | |
| `billing.discount` | discounts up to the login's limit (`02` #12) | yes | off (limit 0) | `billing.sell` |
| `customers.view` | find customers at the counter | yes | **on** | |
| `customers.manage` | add and edit customers | yes | **on** | `customers.view` |

Reasons for the defaults:

- **`billing.sell`, `customers.view`, `customers.manage` on.** A cashier's day is billing, and the billing screen's "add customer" key (`F3`, `02` #7) needs `customers.manage`. Without them a new login is useless.
- **`items.view` and `stock.view` on, nothing that changes or costs.** A cashier answers "do you have it, and how much is it" all day. The purchase price stays off, as `01` #1 and `00` #16 say.
- **`billing.discount` off.** Money leaves the shop through discounts, so the owner turns it on person by person. When the owner switches it on, the screen prefills 5% and the owner can type any limit from 0% to 100%, to two decimals (stored as basis points).
- **Switches depend on a parent.** Turning on a child turns on its parent; turning off a parent turns off its children. The server refuses an inconsistent set with `422`, and ignores a child whose parent is off when it reads (so it stays safe if the data is ever wrong).

## 5. API

All staff routes need `staff.manage`, which only the owner holds, so no staff login can reach them whatever its switches. They run inside `withBusiness` (ADR 0027), act on rows with `role = 'staff'` only (the owner's own row answers `404`), and are written in the P1.4 style (`ZodBodyPipe`, error codes the web app translates, ADR 0036). `ownerPassword` is in the body and checked by the existing `requireOwnerPassword` (rate limit per session; a right password takes the count back). The password hash for a new or reset password is made outside the transaction in the shared Argon2 queue (`hashNewPassword`).

| Route | Needs | Owner's password? | Does |
| --- | --- | --- | --- |
| `GET /api/staff?includeInactive=` | `staff.manage` | no | The staff list: id, name, username, home branch, active, effective permissions, discount limit. |
| `POST /api/staff` | `staff.manage` | yes (question 3) | `{ name, username, password, homeBranchId, permissions?, discountLimitBasisPoints? }`. Omitted permissions take the defaults. Answers the new login. `409 username_taken` (case-insensitive, within the business, deactivated logins included). Logs `staff.created`. |
| `PUT /api/staff/:id` | `staff.manage` | no | `{ name, username, homeBranchId }`. Logs `staff.updated`. No permission change here. |
| `PUT /api/staff/:id/permissions` | `staff.manage` | **yes** (`00` #17) | `{ permissions, discountLimitBasisPoints, ownerPassword }`: the whole switch set. The server stores the difference from the defaults. Logs `staff.permissions_changed` if something changed. |
| `POST /api/staff/:id/password` | `staff.manage` | yes (question 3) | `{ newPassword, ownerPassword }`. Sets it and ends every session of that login (`setPasswordIn`, reason `reset`). Logs `user.password_reset`, `via: owner`. |
| `POST /api/staff/:id/deactivate` | `staff.manage` | no (it only takes access away) | `{ reason? }`. Sets `deactivated_at` and ends the open sessions in the same transaction. Logs `staff.deactivated`. |
| `POST /api/staff/:id/reactivate` | `staff.manage` | yes (question 3) | Clears `deactivated_at`. Logs `staff.reactivated`. |
| `GET /api/session` (changed) | public, as now | | The active session gains `permissions: Permission[]` (everything the caller holds, for hiding screens) and `discountLimitBasisPoints` is now the effective limit. |
| `POST /api/password` (exists) | `session.own` | no | A staff member's own password (`#46`). |

New password rules for staff: `newPassword()` (10 to 128 characters, never trimmed, like every password), and not equal to their username or the business phone number. These fill a gap: `#7` names the email and phone rule for the owner only.

### How a change reaches a session that is already logged in

The server reads the permissions **fresh on every request**. `applyRules` in `session.service.ts` already joins `users` for the deactivation check; it now also selects the three columns, and `callerOf` builds `caller.permissions` from them (the login routes do the same through `startIn`). There is no copy of the permissions in the session row or a cache, so there is nothing to invalidate:

- The staff member's **next request** uses the new set, on every counter they are logged in on. A route they lost answers `403 forbidden`; one they gained works.
- The **screen** learns from `GET /api/session`. The web app re-reads it when the window gets focus, and straight after any `403 forbidden`, then hides what is gone. A cashier in the middle of a bill keeps the bill: only the next save that needs a lost permission is refused (the server re-checks every bill at save, P1.14).
- The discount limit works the same way: P1.14 reads it from the caller at save, so a limit lowered at 10:00 applies to a bill saved at 10:01 whatever the screen showed.
- Deactivation and password reset still end sessions at once (`#34`, `#33`). A permission change doesn't, because the person is still trusted; it only changes what they may do.

Cost: three more columns on a row the request already reads. No extra query.

## 7. Tests (test-first for every rule)

**Shared (Vitest, no database)**

- `effectivePermissions`: defaults only; added; removed; added and removed in the same list (the database also refuses this); an owner-only name (`settings.manage`, `staff.manage`) stored by mistake is ignored; an unknown name is ignored; a child whose parent is off is dropped; `session.own` always present.
- A permission that has a default **on** and is missing from the stored lists is on (the future-module case).
- `normalisePermissions` (screen side): on child turns on parent; off parent turns off children.
- Percent ↔ basis points: `7.5` is 750, `100` is 10000, `100.01` and `-1` and three decimals are refused, no float errors (`0.07` → 7).
- `discountLimit`: switch off is 0; on with null is 0; owner is null.

**Database**

- The new checks: overlap refused; limit outside 0 to 10000 refused; staff without a home branch refused; a login without a username refused; owner with permissions or a limit refused; home branch of another business refused (composite key).
- The tenancy guard test and the entry-log tests pass unchanged.

**API (real database, like the P1.4 tests)**

- Every staff route, as a staff login holding **every** switch: `403 forbidden`. As a locked owner: `401 locked`. Without a session: `401`.
- Create: the new login can log in on the counter; it gets the defaults; the session view's `permissions` match; the discount limit is 0. A custom set is stored as a difference. `username_taken` for `Ramesh` after `ramesh` (case), also against a **deactivated** login; the same username in another business is fine. Short password, the username as password and the phone as password are refused.
- The owner's password: missing, wrong (nothing changes, nothing logged, the count rises), right. Ten wrong tries lock the check for that session (the existing limit). Each gated route is checked, and the two ungated ones (profile edit, deactivate) work without it.
- **Live change:** staff with `items.view` is logged in; the owner removes it; the staff's very next `GET /api/items` is `403` with the **same session cookie**. The reverse: a granted `stock.adjust` works on the next call. Two sessions of one login both change. The session view shows the new list.
- Discount: switch on with 7.5% gives `discountLimitBasisPoints` 750 in the session view; switch off gives 0 even though the limit is stored; turning the switch off and on again keeps the stored limit.
- Dependencies refused with `422`: `items.manage` without `items.view`, `billing.discount` without `billing.sell`. Owner-only and unknown names refused with `422`.
- Deactivate: the staff's open sessions end in the same transaction (`user.logged_out`, cause `deactivated`), login answers `wrong_login`, the history rows stay, the list shows it only with `includeInactive`, reactivate restores login (a new session, the old ones stay ended), and the permissions are as they were.
- Reset password: the old password fails, the new one works, all sessions of that login ended, the owner's own session untouched.
- The owner's row: `PUT`, `deactivate`, `password` on the owner's id answer `404`. Another business's staff id answers `404` and nothing changes (two businesses).
- Entry log: one row per action with the owner as actor, the right `before` and `after`, the branch where it applies, no password or hash anywhere in any row; a save with no change adds no row; a failed save (wrong owner's password, taken username) adds none (it rolls back with the action).
- Staff idle end and other P1.4 rules still pass.

**Web (Vitest and Testing Library)**

- Sidebar and routes by permission: a cashier sees no Settings or Staff; opening `/staff` or `/settings` by address shows "You can't open this page".
- Switch screen: dependency behaviour, the discount box appears only with the switch, "Reset to defaults", save sends the whole set, the dialog appears and the password isn't kept in any state after sending.
- Reset password and deactivate dialogs; a `409 username_taken` shows a field error; three languages have every key.
- A `403 forbidden` makes the session refetch and hides the lost entry; focus refetches.
- My password page for a staff session: works, wrong current password shows an error.

**Real-app check in Chrome (two browsers as two counters):** add a cashier, log in as them on the second browser, take away `items.view` on the first, and see the Items entry go within seconds of focusing the second; deactivate and see the second logged out; the three languages; light and dark; no CSP violations.

## 8. Questions for the owner

**Answered 2026-11-21:** the owner took all seven recommendations (1A, 2A, 3A, 4A, 5A, 6A, 7A). They are `00` #47–#53. 7B (a forced password change) and a "last login" column on the staff list went to the ideas backlog.

Each has a recommended answer. None changes a DECIDED point; they fill in what `00` #16, #17, #33 and #46 leave open, and three of them show where two decided points meet.

1. **What a new staff login can do by default.**
   - A. As in section 4: billing, customers (find and add), items (look only), stock (look only). Everything else off, discounts off. **Recommended:** a cashier can work from the first minute, and nothing that costs money, shows purchase prices or changes stock is on until you switch it on.
   - B. Nothing on; you tick every switch for every new person.

2. **A staff login with discounts switched off.**
   - A. They can still ask for a discount at the counter, and it needs your password (their limit is 0). **Recommended:** this is how billing works today (P1.13's "limit 0 means any discount asks the owner"), and `02` #12 already says going above the limit needs your password; a one-off discount for a regular customer still works while you stand there.
   - B. They can't discount at all; the discount keys are hidden.

3. **Which actions ask for your password** (`00` #17 names permission changes).
   - A. Changing switches or the discount limit, **and** adding a login, resetting a staff password, and reactivating one. Deactivating, renaming and changing the home branch don't ask. **Recommended:** #17 is there so someone at an unlocked owner screen can't give anyone more power; a new login, a new password and a reactivation give the same power, while deactivating only takes it away and you should be able to do it in a second.
   - B. Only changes to switches and the limit, exactly as #17 reads.

4. **Settings and Staff for staff.** `00` #17 says any feature can be switched per login, but Settings holds the recovery key, remembered computers and the business's security times.
   - A. Settings and the Staff page are owner-only and have no switch. **Recommended:** a staff member who could open Settings could reach the recovery key and the staff list, which undoes the password gate.
   - B. Give each login an optional "view Settings" switch (read only).

5. **Where staff change their own password.** `00` #46 says "in Settings", but staff can't open Settings (a note from P1.4's review).
   - A. A small "My password" page every login can open from the name in the sidebar; the owner keeps the same card in Settings, so #46 still holds for the owner. **Recommended:** one shared component, nothing extra for staff to see.
   - B. Staff get a Settings page that shows only the password card.

6. **When a permission change reaches someone who is logged in.**
   - A. On their next click, with no new login; their screen updates when the window gets focus or a request is refused. **Recommended:** it is immediate and costs no extra query; the person isn't thrown out in the middle of a bill, and a bill is checked again when it is saved anyway.
   - B. Only at their next login.
   - C. Their sessions end at once, like deactivation.

7. **A password you set for a staff member** (`00` #33 says you "set a new one").
   - A. You choose it and tell them; they can change it themselves on My password. **Recommended:** it is what #33 says, and it needs no extra login state.
   - B. They must choose their own at the next login. (Safer, but needs a "must change" state and a screen. It can come later; I'll put it in the ideas backlog.)
