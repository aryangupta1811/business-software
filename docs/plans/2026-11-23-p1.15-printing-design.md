## 1. Goal and success criteria

A saved bill prints at the counter with one key, in the right paper size, and can be shared as a PDF on WhatsApp, with Hindi that prints correctly.

Done when:

1. After a save, the receipt prints with no dialog on a counter set up for kiosk printing (ADR 0014), in under 2 seconds.
2. **80 mm** (default), **58 mm** and **A4** layouts come from **one template**, with print stylesheets per size.
3. Every document type prints what the law asks: a **tax invoice** has the CGST Rule 46 fields (supplier's name, address, GSTIN; serial number; date; buyer's GSTIN for B2B, or name and address at ₹50,000 or more; HSN; quantity; taxable value; rate and amount of each tax; place of supply for inter-state; signature line). A **bill of supply** says so and shows no tax. A **plain bill** (unregistered shop) shows neither.
4. The **bill language** (English, Hindi, Hinglish) is a business setting. In Hindi, an item with a Hindi name prints it; GSTIN, HSN, invoice number and amounts stay in Latin digits.
5. **Download PDF** gives the A4 invoice as a PDF that looks the same as the printout, Hindi shaped correctly (क्ष, त्र).
6. **Send on WhatsApp** opens a click-to-chat link with the customer's number and a short message in the bill language (ADR 0049).
7. A **Bills page** lists the branch's bills and can reprint, download and share any of them (question 5).
8. The worker's PDF rendering is measured on the 2 GB server's limits, and the memory numbers are written down (section 6).

## 3. One template, three uses

A new workspace package, **`packages/print`**: React components with no browser-only code, taking a saved bill (the shape `GET /api/bills/:id` returns) and the language.

- **In the browser** (printing): the page renders the template into a hidden `<iframe>` with the stylesheet for the paper size and calls `print()`. With Chrome's `--kiosk-printing` it goes to the default printer with no dialog.
- **In the worker** (PDF): `renderToStaticMarkup` turns the same components into HTML; Chromium loads it with the A4 stylesheet and `page.pdf()`.
- **Fonts:** IBM Plex Sans and Plex Sans Devanagari (ADR 0025), shipped as files in the package. The worker never fetches anything from the network while rendering.

The template only shows numbers that are stored on the bill. It never re-calculates GST: the printout is what was saved (ADR 0047).

**Layouts:**

- **80 mm / 58 mm:** shop header (name, address, GSTIN, phone), document title, number, date and time, cashier, buyer if any; one line per item (name, qty × rate, amount; HSN and GST rate in small type for a tax invoice); totals, discount, the tax table by rate (CGST/SGST or IGST), round-off, grand total, payments (including udhaar and advance once P1.18 lands), change; footer note. 58 mm wraps names and drops the HSN column to a second line.
- **A4:** the same data as a full tax invoice: seller and buyer blocks side by side, a line table with HSN, rate, taxable value and tax columns, the tax summary by HSN and rate, amount in words (Indian numbering, in the bill language), place of supply, signature line.

## 4. Screens

- **"Bill saved"** (P1.14's panel) gains: `P` print receipt, `A` print A4, `D` download PDF, `W` Send on WhatsApp (needs the customer's phone). Auto-print: question 3.
- **Bills page** (`/bills`, sidebar, `Alt+L` if free): the branch's bills newest first, today by default; search by number, customer name or phone, a date range; the same four actions on a selected bill. Permission: `billing.sell` sees their branch's bills (question 5).
- **Settings → Printing:** bill language; the footer note (for example "Goods once sold…", up to 200 characters); a **test print** for each size.
- **This computer:** receipt size (80 or 58 mm) and auto-print, stored on the remembered computer (question 2).
- **Setup guide** in `docs/` (and linked from Settings → Printing): Chrome's `--kiosk-printing` shortcut on Windows, default printer, paper size and margins "None".

## 5. PDFs: the worker, its own image, and a queue job

**Flow** (question 1):

1. `POST /api/bills/:id/pdf` (any login that can see the bill). If the PDF already exists, answer it at once. Otherwise send a `document.render` job (pg-boss, one job per bill and language: `singletonKey`) and answer `202` with `{ status: "rendering" }`.
2. The browser asks `GET /api/bills/:id/pdf` every second (at most 20 s) until it gets the file.
3. The worker takes the job, reads the bill **for that business** (the job carries `businessId`; the worker sets the tenant the same way the api does, ADR 0027), renders the HTML, prints it with Chromium, and saves the PDF.

**Where the PDF is kept:** a new table `documents` (business, kind `bill`, bill ID, language, the bytes, size, created). A bill never changes, so its PDF is made once and kept. Append-only like `bills`. About 40–80 KB each. The nightly dump leaves the bytes out (they can be made again from the bill), so backups don't grow with them.

**The worker's image** (the question in the P1.15 task line): today api, worker and migrate share one image (ADR 0020). Chromium adds about 300–400 MB, which the api and migrate must not carry. `apps/api/Dockerfile` gets a second final stage, `worker`, that starts from the same build output and adds Debian's `chromium` package (it has an **ARM64** build, so it runs on the `t4g.small`) and the fonts. `docker-bake.hcl` builds three images; `deploy/demo/compose.yaml` points the worker at the new one. The api image stays as it is.

**Chromium in a container:** started once per worker and reused (a new page per job, closed after), with `--no-sandbox` only if the container's user can't use the sandbox (to be checked, and explained in the ADR); no network access from the page (`setRequestInterception`, all external requests refused); a 15 s timeout per job; the browser restarted after 200 jobs or on any crash.

## 6. Memory on the 2 GB server

The server has 2 GB of RAM and 2 GB of swap (`infra/terraform/demo/cloud-init.yaml`). Measured locally first, with the containers limited to what the server has:

- idle: api, worker, web, and the worker with Chromium started;
- a PDF rendering while a bill saves (the two together);
- 10 PDFs in a row (looking for a leak).

Numbers go into the ADR and `docs/devops/terraform.md`. If the worker with Chromium goes above about 500 MB, Chromium is started only when a job arrives and closed after a minute idle. Measured on the live server in the Day 13 live run.

## 7. The WhatsApp link builder (`packages/shared`)

`whatsAppLink(phone, text)`: takes a stored 10-digit number (`normalizePhone`), answers `https://wa.me/91<number>?text=<encoded>`. Refuses a number that isn't 10 digits. Message texts live with the screens (three languages); for a bill: "{shop}: your bill {number} for ₹{total}. The PDF is attached." The link never carries anything but the number and that text (ADR 0049). P1.19 reuses it for reminders and statements.

## 8. Tests (test-first)

- Template: each document type shows exactly its required fields and nothing it mustn't (tax on a bill of supply, GSTIN on a plain bill); IGST vs CGST+SGST; the tax table by rate adds up to the bill's stored amounts; amount in words (₹0.50, ₹1,00,000, ₹12,34,567.89 in English and Hindi); Hindi item names in Hindi only; a 58 mm line wraps; B2B buyer and Rule 46 buyer details.
- Bills API: list by branch and date, search, one bill with lines and payments; another branch's bill per the switch rules; two businesses kept apart.
- PDF: the job made once per bill and language; a second request while rendering doesn't send a second job; the worker reads only the job's business; the file starts with `%PDF`; Hindi text is in the PDF (the font embedded, extracted text matches); timeout and a Chromium crash leave the job retryable.
- `whatsAppLink`: encoding of `₹`, `&`, `#`, line breaks and Hindi; a bad number refused.
- Settings and "this computer": who may change them, logged.

## 9. Questions for the owner

**Answered 2026-11-23:** the owner took all seven recommendations (1A to 7A). They are `02` #28–#34.

Each has a recommended answer. None changes a DECIDED point.

1. **How a PDF is made.**
   - A. In the worker with Chromium (its own image), by a queue job, kept in the database once made. **Recommended:** it's what ADR 0014 decided; it keeps Chromium out of the api; the statement PDF (P1.19) and salary slips (P2.5) reuse the same job; and it's a real use of the job queue to show in interviews.
   - B. The browser's own "Save as PDF" from the print dialog. Nothing on the server, but it's three clicks, and with kiosk printing switched on the dialog never appears, so it doesn't work on the counter.
   - C. A ready-made PDF container (Gotenberg) next to the worker. Less code, but one more container on a 2 GB server and less to explain.

2. **Receipt size and auto-print are set per…**
   - A. **Computer** (stored on the remembered computer). **Recommended:** the printer belongs to the counter; a shop can have an 80 mm printer at one counter and a 58 mm one at another.
   - B. Business, one setting for every counter.

3. **Printing after a save.**
   - A. Auto-print on by default: the receipt prints the moment the bill is saved; `P` reprints. **Recommended:** most shops print every bill, and it saves a key at the busiest moment.
   - B. Off by default: `P` prints.

4. **A bill with a buyer's GSTIN (B2B).**
   - A. Prints on **A4** by default, even at a receipt counter; `P` still gives the receipt. **Recommended:** ADR 0014 says A4 is for B2B bills; a business buyer files it for their input tax credit.
   - B. Always the computer's receipt size; `A` for A4.

5. **The Bills page: who sees what.**
   - A. Staff with "Sell at the counter" see their branch's bills; the owner sees every branch's. Reprints are in the entry log. **Recommended:** a cashier must be able to reprint for a customer who comes back, and the log shows who printed what.
   - B. Only the owner sees the Bills page; staff reprint only from "Bill saved".

6. **A reprinted bill.**
   - A. A reprint says "Reprint" and its date under the title. **Recommended:** the customer can't pass a second copy off as a second purchase, and the shop knows a copy from the original.
   - B. A reprint looks exactly like the first print.

7. **The PDF's language.**
   - A. Always the business's bill language. **Recommended:** one setting, the same as the printout.
   - B. Chosen each time it's downloaded.

## 11. Build notes (PR 1, 2026-11-24; from the lane that started it, not reviewed yet)

Nothing here changes section 9's answers.

**Question for the owner:** `02` #30 and #31 say `P` reprints and gives the receipt. ADR 0026 refuses plain letters as shortcuts (the search box is always focused at the counter, so `P` would type "Parle"). This was a mistake in section 4. Proposal: `Alt+P` receipt, `Alt+A` A4, `Alt+W` Send on WhatsApp; `Alt+D` download in PR 2. **Answered 2026-11-24 (`02` #30, #31): as proposed, and `Alt+V` for the Bills page.** `Alt+A` is already used inside the payment dialog only. Bills page: `Alt+V` proposed (`Alt+L` is Lock now, `Alt+T` is Attendance).

**Check against the requirements in review:** the lane planned a bill of supply with no HSN. `02` #24 asks for HSN on every line of a *regular* business's bill, so confirm which applies before building it.

**Findings:**
- **CSP** (`apps/web/Caddyfile`, `style-src 'self'`): an iframe `srcdoc` inherits it, so an inline `<style>` is blocked. Plan: classes only in the template (a test asserts no `style=`), the print CSS through `adoptedStyleSheets`, and a `<style>` fallback for jsdom. To be proven in Chrome against the Caddy build, not only the dev server.
- **Fonts:** reuse the web app's `@fontsource` files (IBM Plex Sans latin and Plex Sans Devanagari, 400/500/600). `printCss(size, urlOf)` takes a URL resolver so the worker (PR 2) can pass file paths.
- **Shop phone:** a saved bill's `seller` has none. Plan: store it at saving (`apps/api/src/bills/bills.service.ts`, jsonb, no migration); older bills print without it.
- **Customer phone** for search and WhatsApp comes from `customers` through the bill's `customerId`; `buyer` has none.
- **Views:** `printing` (receipt size, auto-print) goes in `ActiveSession` and `DeviceView`, so a cashier's counter can auto-print without `settings.view`; language and footer note come with `GET /api/bills/:id`.
- **Bills list:** a cursor on the uuidv7 `id` (`?after=`), `bills_branch_idx`, `branchScope(caller, query.branch, 'caller')`.
- **Template plan:** plain bill: no GSTIN, tax or HSN; amount in words, tax summary and signature on A4 only; GSTIN, HSN, CGST, SGST and IGST in Latin in every language; Hindi item names only when the language is `hi`; an unknown payment mode prints as stored.
