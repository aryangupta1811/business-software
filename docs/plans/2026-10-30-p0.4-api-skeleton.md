# P0.4 API Skeleton Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A NestJS `api` with `GET /api/health` (alive) and `GET /api/health/ready` (alive and the database answers), a `worker` entry point and a one-shot `migrate` entry point, all from one Docker image, started by `docker compose up` after migrations succeed.

**Architecture:** Internal packages (`shared`, `db`) compile to `dist/` with TypeScript project references (`tsc -b`); a `source` export condition lets Vitest, ESLint and the editor read their `.ts` files without a build. `packages/db` gains the database client and the migration runner. `apps/api` is written by hand (no `nest new`) and has three entry points: `main.ts`, `worker.ts`, `migrate.ts`. Compose runs `migrate` as `app_owner`, then `api` and `worker` as `app_runtime`.

**Tech Stack:** NestJS 12.3 (ESM) on Express (`@nestjs/platform-express`), NestJS's built-in `ConsoleLogger` (JSON in containers), drizzle-orm 0.45 + `pg` 8, TypeScript ~6.0 project references, Vitest 5, Testcontainers, Docker multi-stage build on `node:24-slim`, Docker Compose.

**Spec:** `docs/PROGRESS.md` task P0.4 (including its four open decisions); ADRs 0004 (NestJS, api + worker from one image), 0007 (no DELETE for the runtime role), 0010 (pg-boss, outbox), 0013 (testing), 0019 (roles, `pg`, Drizzle); the owner's secrets requirement (session 5, below).

## Global Constraints

- **Secrets never reach anyone who can read the public repo** (owner, session 5). Concretely:
  - no secret in git, in the Docker image (no `COPY` of `.env*`, no secret `ARG`/`ENV`; values arrive only when the container starts), in logs, or in error messages;
  - config errors name the variable, never its value (`DATABASE_URL` contains a password);
  - recorded in a new `docs/devops/secrets.md`, which also sets the rules for the browser (P0.5: never a `VITE_` secret), CI (P0.6: no secrets for fork PRs, no `pull_request_target`) and the Claude API key (Phase 3: server only, SSM, spend limit).
- The app connects as `app_runtime` only. Only `migrate` uses `app_owner` (`MIGRATION_DATABASE_URL`). No fallback from one URL to the other.
- Published ports bind `127.0.0.1` only. Containers run as the non-root `node` user.
- Production code runs compiled JavaScript from `dist/`; Node never strips TypeScript at runtime.
- `pnpm lint`, `pnpm typecheck` and `pnpm test` work on a fresh clone without a build first.
- One HTTP prefix: `/api` (Caddy routes `/api` to this service later; ADR 0011).
- Never `docker compose down -v` (deletes the local database) without the owner's OK.
- New `.ts` files sit inside a tsconfig `include`. New install scripts: decide each with a reason in `pnpm-workspace.yaml`.
- Before each commit: gitleaks staged scan + personal-data `git grep` (`docs/devops/git-workflow.md`). Conventional Commits. **No AI attribution lines** (`CLAUDE.md` rule 6).

## Decisions in this plan (and why)

| Decision | Why |
| --- | --- |
| Compile internal packages with project references (`tsc -b`), exports `source` → `src`, `types`/`default` → `dist` | NestJS needs a compiler anyway (decorator metadata). `tsc -b` builds `shared` → `db` → `api` in order, incrementally, and one `tsc -b -w` watches them all. Rejected: bundling (one more tool, harder stack traces); Node type stripping (refused inside `node_modules`, where packages sit in the image). → ADR 0020 |
| Express adapter, not Fastify | Speed doesn't matter at a shop counter; Express is Nest's default and what docs and examples assume. → ADR 0020 |
| NestJS `ConsoleLogger({ json })`, not pino | No extra dependency; JSON lines in containers are what stage 9 needs. → ADR 0020 |
| Hand-written `apps/api`, not `nest new` | `nest new` adds Jest, its own ESLint and Prettier, all of which we'd delete. About eight files are needed. |
| `node:24-slim` multi-stage image | Debian, like `postgres:18`; build tools stay in the build stage; runtime runs as `node`. → ADR 0020 |
| One-shot `migrate` container (same image, `node dist/migrate.js`, as `app_owner`); `api` and `worker` wait for `service_completed_successfully` | The schema is upgraded before new code serves requests, by the only role allowed to change it. Same mechanism locally and on EC2 (stage 6). Locally `pnpm db:migrate` (drizzle-kit) stays; both use Drizzle's journal table. → ADR 0021 |
| Rule: rebase a migration PR on `main` before merging; regenerate if `main` got a newer migration | Drizzle 0.x silently skips a migration older than the newest applied one. → ADR 0021, `git-workflow.md` |
| pg-boss gets its own role `app_queue` owning only schema `pgboss`; built in P2.7, not now | pg-boss 12.38 creates tables at run time (partitioned queues, `queue_stats` partitions) and deletes job rows, so it needs DDL and DELETE. Sandboxing it in its own schema keeps "the runtime role can't delete business rows" literally true. The API never touches pg-boss (outbox rows only). Rejected: owner installs pg-boss SQL and runtime gets DELETE on `pgboss.*` (breaks on run-time DDL; every upgrade a hand-made migration). → ADR 0022 |
| `pool.on('error')` handler is a required argument of `createDatabase` | `pg` emits `error` when an idle connection dies (database restart); unhandled, that kills the Node process. Making it required means no caller can forget. |

Not in this task: tables and RLS (P1.1); pg-boss and `app_queue` (P2.7); CI (P0.6); the web app (P0.5). The first class-injected Nest service (P1.x) must prove Vitest keeps decorator metadata (ADR 0013 names the SWC plugin; check whether Vitest 5's own transform already does it before adding it, and raise the result with the owner).

## Review Focus

1. **The database restarts while the API runs:** the process stays up, `/ready` answers 503 while it's down and 200 again afterwards. → Task 1 test (killed idle connection), Task 4 smoke step.
2. **A missing or malformed env var:** startup fails with a message naming the variable, and the message never contains the password. → Task 2 config tests.
3. **The database is unreachable at startup:** the API still starts, `/health` is 200, `/ready` is 503 (no crash loop). → Task 2 test.
4. **`docker compose stop`:** `api` and `worker` exit within a second or two with code 0 (SIGTERM handled), not killed after 10 s. → Task 4 smoke step.
5. **A failing migration:** `migrate` exits non-zero with a message without the password, and `api`/`worker` don't start. → Task 4 smoke step.
