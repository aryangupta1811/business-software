# Stage 6 — Continuous deployment (design, for the owner's OK)

**Date:** 2026-11-19 · **Status:** built on `feat/stage-6-cd` (workflows and scripts); Terraform planned, not applied; no deploy yet · ADR 0012 (CI/CD with OIDC), ADR 0034 (images and Run Command deploy), ADR 0037 (backups)

## Goal

Every merge to `main` can reach the demo server with one click from the owner, with:

- no AWS keys anywhere;
- a health check;
- automatic rollback to the previous release;
- a fresh backup first.

The image that runs on the Graviton server is the exact image that was smoke-tested.

## How a deploy flows

```text
merge to main
  → images workflow (ubuntu-24.04-arm): build both images → load locally → smoke test (compose + smoke.sh) → push the tested images to GHCR
  → deploy workflow (workflow_run: images succeeded on main)
      job "deploy", environment "demo" → waits for the owner's approval (the manual go-ahead)
        1. deploy hold check (repository variable DEPLOY_HOLD)
        2. AWS credentials through OIDC (role business-software-demo-deploy, 1 hour)
        3. is the server running? if not: fail with "start RDS, then EC2"
        4. record the release now on the server (release.env) = rollback target
        5. backup now (stage 7's service; the deploy stops if it fails)
        6. scripts/deploy/demo.sh <commit>  (install.sh: migrate, compose up --wait, api healthcheck)
        7. scripts/deploy/check-live.sh (HTTPS, readiness, headers) from the runner
        8. on failure in 6 or 7: demo.sh <previous commit>, then check-live again; the job stays red
```

`workflow_dispatch` with a `commit` input deploys any commit already on `main`, through the same approval. That is also the manual rollback.

## Rollback, and its limit

- **What rollback does:** it redeploys the previous commit's images.
- **Migrations only go forward, so rollback runs old code on the new schema.** This is only safe if every migration is backward-compatible with the release before it: **expand, then contract**. For example:
  1. add a column, and release the code that uses it;
  2. drop the old column only in a later release.
- **Rule for every PR with a migration:** "can the previous release run on this schema?" goes in the PR template.
- **When the answer is no:** the pre-deploy backup (step 5) plus the restore runbook (`docs/devops/backup-restore.md`) is the way back. That needs the owner's OK (rule 7).

## The deploy hold

- **Two locks:**
  1. **Repository variable `DEPLOY_HOLD`. It fails closed:** the job deploys only while it is exactly `off`. Any other text is the hold's reason, printed as the job's error before it touches AWS, e.g. "P1.3 signup has no rate limit until P1.4". Unset also holds ("DEPLOY_HOLD is not set"), so a merge before the environment is set up can't deploy. (Built 2026-11-19: the design first said "deploys while empty", which would have deployed from an environment nobody had set up.)
  2. **The approval itself.** Nothing reaches the server without the owner's click, even when the variable is empty.
- **Merges while the server is stopped:**
  - The job just waits for approval. GitHub keeps a pending deployment for up to 30 days.
  - The owner starts RDS, then EC2, then approves.
  - Only the newest waiting deploy matters: an older pending one can be rejected.

## What the owner does (after the OK)

1. **Approve `terraform apply`** of the 3 resources.
2. **Set up the GitHub environment.** Claude runs these `gh api` calls with the owner's OK:
   1. Create environment `demo`.
   2. Required reviewer: the owner.
   3. Deployment branches: `main` only.
   4. Secret `AWS_DEPLOY_ROLE_ARN`, from `terraform output -raw deploy_role_arn`. Pipe it straight in, never print it.
   5. Variable `DEMO_INSTANCE_ID`.
   6. Repository variable `DEPLOY_HOLD`, with the reason as its text (`off` lifts it).
3. **First run:** merge stage 6, approve the deploy, and watch it get refused by the hold.
4. **After P1.4 merges** (it has, with stage 7: 2026-11-19): set `DEPLOY_HOLD` to `off`, approve a real deploy, then prove the way back. `workflow_dispatch` with the previous commit is the manual rollback. The automatic one is proven by its test: the deploy step forced to fail in a dry run against the live server, with the previous release coming back and `check-live.sh` green.

## What was built (2026-11-19)

- `.github/workflows/images.yml`: one ARM64 job builds both images into the runner's Docker, runs the CI smoke test on them (`compose up --wait`, `scripts/ci/smoke.sh`), then tags and pushes those same images.
- `.github/workflows/deploy.yml`: the flow above. Details the design left open:
  - the live check gets three tries, 15 s apart, so a slow restart doesn't trigger a needless rollback;
  - rollback runs only if the deploy or the live check failed, never after a failed backup (nothing was deployed then), and only when a release was running before;
  - the checkout is `main` with full history, so `demo.sh` can check the commit is on `main`; a dispatch from another branch can't get the environment, which accepts `main` only.
- `scripts/deploy/lib.sh`: `aws_cli` names the profile on the laptop and uses the workflow's credentials in GitHub Actions; the instance ID comes from `DEMO_INSTANCE_ID` when set; `cygpath` and `python` only on Windows (`python3` on Linux).
- `scripts/deploy/current-release.sh` (new): the commit the server runs now, or nothing.
- `scripts/deploy/backup.sh before-deploy`: like `now`, but skipped when the server has no backup service yet. The first deploy after stage 7 is the one that installs it.
- `deploy/demo/install.sh`: keeps the replaced release as `previous-release.env`.
- The PR template asks whether the previous release still runs on the new schema.

**Tested:** actionlint (with shellcheck on every `run:` block) and shellcheck on the scripts; the scripts on Linux against a fake AWS CLI (no `--profile` in CI and the profile named on the laptop, the instance from `DEMO_INSTANCE_ID`, valid Run Command JSON, the running release read back, empty on a new server) and on Git Bash (Windows path for the parameters file). Not testable before the owner's setup: the OIDC role (needs the apply), the environment's approval, and a real deploy and rollback. Those are the owner's steps below.

## Not in this stage

- Staging environment (ADR 0011: only to rehearse a risky change).
- Blue/green or zero-downtime swaps: `install.sh` restarts the stack, a few seconds of downtime. Fine for a demo.
- Alerts on a failed deploy beyond GitHub's own email: stage 9.

## Interview note

Merging to main builds and smoke-tests the ARM64 images on GitHub's ARM runner, pushes exactly those images, then waits for my approval in a protected GitHub environment. The deploy job logs in to AWS through OIDC, a one-hour role that only trusts that environment, takes a backup, deploys through Systems Manager (no SSH, no keys) and checks the live site. If anything fails it redeploys the previous release. Rollback is only safe because migrations are expand-then-contract, and the backup covers the rest.
