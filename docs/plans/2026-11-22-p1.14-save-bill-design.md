# P1.14 Saving a bill — Design

**Status:** approved; the owner took all three recommendations on 2026-11-22 (section 9: option A, taxable value, the selling branch's GSTIN; `00` #61, `02` #25–26). **Date:** 2026-11-22 (session 30).
**Requirements:** `02` #1–6, #10–14, #24–25; `00` #8, #36, #58, #60; `01` #12. **ADRs:** 0001, 0007 (rules 3–7), 0027, 0041, 0043, 0045, 0046.
**Builds on:** P1.13's `billDraftSchema`, `cartToBillInput`, `discountWithinLimit` (`packages/shared/src/billing.ts`, design `2026-11-20-p1.13-billing-design.md` §10), `moveStock` (P1.8), alerts in `moveStock` (P2.7), the branch code (P1.6), the session's discount limit (P1.5).

## 1. Goal

`F10` → Enter on a paid bill saves it: one transaction that numbers the bill, stores it for good, takes the stock out and logs it. A retry never makes a second bill, two counters never get the same number, and a failed save leaves no gap in the numbers. The browser's numbers are never trusted.

Done when: the counter saves a bill and shows its number; every rule below has a test; the two-counter tests pass; the Chrome check shows it in three languages.

## 3. The save, step by step (one transaction, `withBusiness`)

1. **Same bill key already saved?** Return that bill (`201`, the same answer, as a stock retry does; built: Nest sets the status after the handler, so one code keeps it simple) if the request is the same (a hash of the normalised draft is stored); a different request with the same key answers `422 key_reused`. Two retries racing: the unique `(business_id, bill_key)` makes the second insert fail; it rolls back, reads the first and answers it.
2. **Read the business and the caller's branch** (scheme, `negative_stock`, `features`, branch state, code, GSTIN, address). The branch is always the session's computer branch (ADR 0045).
3. **GSTIN gate** (`02` #25, `00` #36): a regular or composition business needs a GSTIN on the selling branch (question 3) → else `409 gstin_required`.
4. **Re-read every item, pack and price** (`FOR SHARE`, the same lock `moveStock` takes) and build the catalogue map the shared code reads. `wholesale` without the `wholesale_price` feature → `422`.
5. **Re-price:** `cartToBillInput` + `calculateBill` with the server's own scheme and states. If any line's price differs from `shownUnitPricePaise`, or the grand total from `shownGrandTotalPaise` → **`409 prices_changed`** with each line's current price and the new grand total. Nothing is written. (An archived item or a missing GST rate answers `409 items_unavailable` with the line numbers.)
6. **Payments** re-checked with `paymentIssues` against the server's grand total (equal by now).
7. **Customer** (if any): must exist and not be archived. B2B (a GSTIN) or the place of supply is checked against it as P1.13 does. **Rule 46** (regular scheme): an unregistered buyer with a **taxable value of ₹50,000 or more** needs name, address and state (question 2) → else `422 buyer_details_required`.
8. **Discount limit:** `discountWithinLimit(input, caller.discountLimit)`. Over it: needs `approvalId` → the approval must be this business's, this branch's, this `billKey`, kind `discount`, not expired, `used_at` null, and its shares must cover `discountShares(input)`. It's marked used (`update … where used_at is null returning`, so two saves can't both use it). Else `403 approval_required` / `409 approval_invalid`.
9. **Held bill** (`heldBillId`): must be this branch's, the same `billKey`, and already resumed (resuming closed it). Stored as a link only.
10. **Number** (section 5): `insert … on conflict (business_id, branch_id, financial_year) do update set last_number = last_number + 1 returning last_number`. The row lock is held to commit, so a rollback in any later step gives the number back: **no gaps** (ADR 0007 rule 5). The counter is taken **after** every check that can fail, so other counters wait on the lock as short a time as possible.
11. **Write** the bill, its lines and payments.
12. **Stock out:** one `moveStock` call (kind `sale`, `belowZero` = the business's setting) for goods lines; services skip it. A pack sells `quantity × pack size` stock units. `block` and short → `StockRuleError('below_zero')` → `409 stock_short` with the items, and the whole save rolls back (number included). `warn` lines come back in the answer. Alerts follow inside `moveStock`.
13. **Log** `bill.created` (new action): number, totals, line count, every discount (`02` #12), approval id, held bill id, warned lines.
14. Answer `201` with the bill (section 6).

## 4. Data (migration `0017`)

Every table follows ADR 0027 (`id()`, own `business_id`, `tenantPolicies` with `backup_read`, hand-written `FORCE`, composite keys, `unique (business_id, id)`).

**A saved bill is never edited (`02` #14), so the database enforces it:** `bills`, `bill_lines` and `bill_payments` are **append-only** like `entry_log` and `stock_movements` (the migration revokes UPDATE; DELETE was never granted; on the guard's `APPEND_ONLY` list). P1.16 records a cancellation as a row in its own table, not a change to the bill. This is an ADR (0047).

**`invoice_counters`** — `branch_id`, `financial_year` (`2026-27`), `last_number` int; unique `(business_id, branch_id, financial_year)`. Updated in place (it's a counter, not a record).

**`bills`**
| Column | Rule |
| --- | --- |
| `branch_id`, `bill_key` (unique per business), `request_hash` | idempotency |
| `financial_year`, `sequence`, `number` | unique `(business, branch, year, sequence)` and `(business, number)` |
| `document` | `tax_invoice` / `bill_of_supply` / `bill`, from the scheme |
| `business_date` | IST day (`businessDate`), as stock movements |
| `price_list`, `supplier_state_code`, `place_of_supply_state_code`, `tax` | as the engine |
| `customer_id` null + `buyer` jsonb null | a **copy** of name, GSTIN, legal name, address, state at saving, because a customer can change later and the bill must not |
| `seller` jsonb | the branch's name, address, GSTIN, licences at saving, for the same reason |
| `gross_paise` … `round_off_paise`, `grand_total_paise` | the engine's totals |
| `bill_discount` jsonb null, `approval_id` null, `held_bill_id` null | |
| `created_by`, `created_at` | |

**`bill_lines`** — `bill_id`, `line_no`, `item_id`, `pack_id` null, a copy of the name, Hindi name and unit, `hsn`, `rate_basis_points`, `price_includes_tax`, `quantity_thousandths`, `stock_quantity` (stock units, null for services), `unit_price_paise`, `discount` jsonb null, every engine line amount, `unit_cost` (null for services; the cost is what medical profit and P2.9 read). Built: a line's movement is found by `stock_movements.bill_id` and the item, so no `stock_movement_id` column.

**`bill_payments`** — `bill_id`, `mode`, `amount_paise`, `tendered_paise` null, `reference` null.

**`stock_movements`:** kind `sale` added, and a `bill_id` column (composite key to `bills`) so a sale's movements point at their bill.

## 5. Invoice numbers — the 16-character problem

**Rule 46(b)** of the CGST Rules: a tax invoice carries "a consecutive serial number not exceeding **sixteen characters**, in one or multiple series, containing alphabets or numerals or special characters hyphen or dash and slash", unique for a financial year. The decided example in `00` #58, `ABC/AND/2026-27/001`, is **19 characters**. A prefix, a branch code (up to 6 characters, P1.6), the year and a number that can grow past 999 can't all fit. The owner chooses (question 1).

Whatever the format: one series per branch per financial year (April to March, from the business date), starting at 1; the number is built from the prefix and branch code **at saving** and stored, so a later settings change never renumbers old bills; Settings shows a live example and refuses a prefix that could make a number pass 16 characters at 99,999 bills.

## 6. The answer and the counter

`201 { id, number, document, businessDate, grandTotalPaise, changePaise, warnings: [{ itemId, balanceAfter }] }` (`SavedBillView`), read back from the stored rows so a retry gets the same. Other answers built: `409 customer_unavailable` (deleted or archived customer), `422 place_of_supply` (a business customer's bill supplied neither in their state nor at the counter), `422 held_bill_invalid`, `422 wholesale_off`, `422 invalid_quantity` (e.g. half a piece). P1.15 prints from `GET /api/bills/:id` (added there).

**Web (PR 2):** Enter on a paid bill (the payment panel's "Ready to save") → `POST /api/bills`. While it's in flight the button is busy and the bill can't change; a lost connection retries with the **same bill key** (safe, section 3.1). On `201`: a "Bill saved, ABC/26-27/42" state with the change due and `Alt+N`/Enter for the next bill; the open bill, its held copy key and its approval are cleared. On `409 prices_changed`: sync the catalogue, re-price, highlight changed lines, the cashier confirms and pays again. `stock_short`, `approval_required`, `gstin_required`, `buyer_details_required` each show their message where the fix is (the line, the discount, Settings, the customer box). Three languages.

## 7. Tests (test-first)

- **Shared:** financial year from a date (31 March / 1 April IST), number formatting and its 16-character check, pack → stock quantity.
- **Database:** append-only (UPDATE and DELETE refused, `42501`); the guard lists the new tables; `bill_id` key on movements.
- **API, rules:** each answer in section 3 (prices changed, archived item, GSTIN gate, Rule 46 at ₹49,999.99 and ₹50,000 taxable, discount over limit without/with/expired/used/other-bill approval, payments, wholesale without the feature, held bill of another branch, retry same → same bill, retry different → `key_reused`); `warn` vs `block`; services don't move stock; the bill's totals equal `calculateBill`'s; the log entry's fields.
- **Concurrency (two counters, real PostgreSQL):** 20 saves at once at one branch → numbers 1–20, no gap, no duplicate; the same bill key twice at once → one bill; a save that fails after taking a number (stock `block`) → the next bill gets that number; two counters selling the last unit under `block` → one bill, one `stock_short`; two branches don't wait on each other's counter; an approval used by two saves at once → one succeeds.
- **Web:** the save flow, the busy state, retry with the same key, each error's message.
- **Chrome:** the real app, three languages, light and dark, 1024 px.

## 9. Questions for the owner

1. **Invoice number format** (Rule 46's 16 characters; `00` #8, #58 change).
   - **A (recommended):** one label, then the short year, then the number: `ABC/26-27/42` with one branch (the label is the business's prefix, up to 4 characters, optional: `26-27/42` without one), `AND/26-27/42` with 2+ branches (the label is the branch code, so branch codes used in numbers become 1–4 characters). Longest: 4 + 1 + 5 + 1 + 5 = 16 at 99,999 bills a branch a year. No zero padding.
   - **B:** keep prefix and branch code, drop the year (the law allows it; the date on the bill tells the year, and numbers restart every April): `ABC/AND/42`. Prefix up to 3, codes up to 4.
   - **C:** the decided format as written. Not legal for numbers over 16 characters; not recommended.
2. **Rule 46's ₹50,000:** the rule counts the **taxable value** (before GST), P1.13's design says "total". **Recommended: taxable value**, as the rule says; the counter's prompt follows the same number.
3. **Which GSTIN must exist before the first tax invoice:** `02` #25 says the head office's. A bill prints the **selling branch's** GSTIN (ADR 0045), and a branch in another state has its own. **Recommended: the selling branch's** (for a one-branch business that is the head office, so nothing changes).
