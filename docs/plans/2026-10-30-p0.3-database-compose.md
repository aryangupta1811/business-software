# P0.3 Database + Docker Compose Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `pnpm db:up` starts PostgreSQL 18 in Docker Compose with two app roles: a migration role that owns the schema, and a runtime role that cannot delete. `pnpm db:migrate` applies the first Drizzle migration. An integration test on a throwaway Testcontainers database proves the roles and grants.

**Architecture:** One-time setup that needs an administrator lives in a bootstrap SQL file that creates the roles and the database. Docker runs it on a fresh volume, Testcontainers runs it in tests, and later it is run once by hand on RDS. Everything inside the database is a Drizzle migration, run as the migration role. A new workspace package, `packages/db`, holds the schema, the migrations, the bootstrap file and the integration test, so that the API, the worker and the seed scripts (P0.4, ADR 0016) can share them.

**Tech Stack:** PostgreSQL 18 (`postgres:18` Debian image), Docker Compose, drizzle-orm 0.45 + drizzle-kit 0.31 (latest stable), `pg` (node-postgres) 8, `@testcontainers/postgresql` 12, Vitest 5.

**Spec:** `docs/PROGRESS.md` task P0.3; ADR 0005 (PostgreSQL + Drizzle), ADR 0006 (roles, RLS), ADR 0007 (no `DELETE` for the runtime role), ADR 0013 (Testcontainers), `docs/devops/DEVOPS_PLAN.md` stage 2.

## Global Constraints

- PostgreSQL major version **18**: the newest version RDS supports (18.1–18.4). One image tag, `postgres:18`, written once in `compose.yaml`. The integration test reads it from there, so local and tests can't drift apart (ADR 0005).
- Role names: `app_owner` (migrations; owns the database and its tables) and `app_runtime` (the app). Both `NOSUPERUSER NOCREATEDB NOCREATEROLE NOBYPASSRLS`. Database name: `business_software`.
- `app_runtime` gets `SELECT, INSERT, UPDATE` on tables, and nothing else: no `DELETE`, `TRUNCATE`, `REFERENCES`, `TRIGGER`, and no `CREATE` anywhere (ADR 0007 rule 1).
- Passwords live only in `.env` (git-ignored) and in the test's throwaway container. `.env.example` holds placeholders. Use letters and digits only, because they go inside URLs.
- The database port is published on `127.0.0.1` only, never `0.0.0.0`.
- `docker compose down -v`, deleting the `pgdata` volume, or any `DROP` on a non-scratch object needs the owner's OK first (`CLAUDE.md` rule 7).
- Every new `.ts` file must be inside its package's tsconfig `include`, or type-aware lint fails.
- Scripts must run in PowerShell and on Linux CI. Docker Desktop must be running (`pnpm check` now starts containers).
- Before each commit: gitleaks staged scan + personal-data `git grep` (`docs/devops/git-workflow.md`, Secrets). Conventional Commits. **No AI attribution lines** (`CLAUDE.md` rule 6).
- Dependencies' blocked build scripts stay blocked unless something fails without them. Write down any that pnpm lists.

## Decisions in this plan (and why)

| Decision | Why |
| --- | --- |
| Debian `postgres:18`, not `-alpine` | RDS runs on glibc. Alpine uses musl, which sorts text differently. Hindi item names must sort the same locally and in the cloud. |
| Volume mounted at `/var/lib/postgresql`, not `.../data` | Postgres 18 images moved the data folder to `/var/lib/postgresql/18/docker`. The old mount path would leave the real data in an anonymous volume, which a `compose down` loses. |
| Roles and the database come from a bootstrap SQL file, not a migration | Creating roles and databases is server-wide and needs an administrator, and passwords must not be in git. The migration role stays powerless outside its own database. |
| Runtime grants via `ALTER DEFAULT PRIVILEGES` in migration `0000` | Every future table automatically gets `SELECT, INSERT, UPDATE` for the runtime role and never `DELETE`. Nobody has to remember a `GRANT` per table. |
| `pg` (node-postgres), not `postgres.js` | It's the most widely used driver, and pg-boss (ADR 0010) already uses it: one driver for the whole app. |
| drizzle-orm 0.45 (stable), not 1.0-rc | Don't build on a release candidate. 1.0 changes the migration folder layout, and `drizzle-kit up` converts it when we upgrade. |
| `drizzle-kit migrate` for local migrations; the code migrator (`migrate()`) only in tests | No Node runner script yet: Node can't run our TypeScript sources (the P0.4 problem). P0.4 decides how production runs migrations. |
| Integration tests run inside `pnpm test` | One command checks everything (ADR 0013). The cost is that `pnpm check` needs Docker running, which gitleaks already does. |
| Healthcheck uses `pg_isready -h 127.0.0.1` | During first start, the image runs init scripts on a temporary server that only listens on a socket. A socket check would say "ready" too early. TCP is ready only after init has finished, so `pnpm db:up && pnpm db:migrate` is safe. |

Not in this task: tables, Row-Level Security and `set_config` (P1.1); a database client for the app and a production migration runner (P0.4); API containers (P0.4); CI (P0.6).

## Review Focus

1. **Data survives `docker compose down` and a restart.** A marker table is still there after `down` + `up`. → Task 1, Step 5.
2. **First start on an empty volume:** `pnpm db:up` returns only once roles and the database exist, so the next command can connect as `app_owner` over TCP. → Task 1, Step 4.
3. **A password missing from `.env`:** Compose refuses to start and names the variable, instead of creating a role with an empty password. → Task 1, Step 6.
4. **Only this computer can reach the database:** the port is bound to `127.0.0.1`. → Task 1, Step 4.
5. **The runtime role can't touch migration bookkeeping or the schema:** it can't read `drizzle.__drizzle_migrations`, create or drop tables, delete or truncate. Running migrations twice changes nothing. → Task 2 tests.

### Task 1: PostgreSQL in Docker Compose with app roles

**Files:**
- Create: `compose.yaml`, `.env.example`, `packages/db/bootstrap/create-roles.sql`
- Create (git-ignored, never committed): `.env`
- Modify: `package.json` (root scripts)

**Interfaces:**
- Produces: Compose service `db` (image `postgres:18`, written exactly as `image: postgres:18` on its own line, which Task 2 reads); env vars `POSTGRES_PASSWORD`, `APP_OWNER_PASSWORD`, `APP_RUNTIME_PASSWORD`, `MIGRATION_DATABASE_URL`; roles `app_owner`, `app_runtime`; database `business_software`; root script `pnpm db:up`.

- [ ] **Step 1: `packages/db/bootstrap/create-roles.sql`.** A psql script. Read passwords with `\getenv owner_password APP_OWNER_PASSWORD` and `\getenv runtime_password APP_RUNTIME_PASSWORD`, and use them as `:'owner_password'` (psql quotes them safely). Then:
  - create both roles with the attributes in Global Constraints, both `LOGIN`;
  - `CREATE DATABASE business_software OWNER app_owner`;
  - `REVOKE ALL ON DATABASE business_software FROM PUBLIC`; `GRANT CONNECT ON DATABASE business_software TO app_runtime`;
  - `\connect business_software`, then `REVOKE CREATE ON SCHEMA public FROM PUBLIC` (already the default since PG 15; written out so the intent is visible).

  Start the file with a comment: who runs it (an administrator, once per server), that Docker runs it only on an empty volume, and that on RDS it is run by hand at DevOps stage 5.

- [ ] **Step 2: `compose.yaml`.**
  - `name: business-software`, so volume names don't depend on the folder name.
  - One service, `db`, with `image: postgres:18`.
  - `environment`: `POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?set POSTGRES_PASSWORD in .env}`, and the same `:?` form for `APP_OWNER_PASSWORD` and `APP_RUNTIME_PASSWORD`.
  - `ports: ["127.0.0.1:5432:5432"]`.
  - `volumes`: `pgdata:/var/lib/postgresql`, plus `./packages/db/bootstrap/create-roles.sql:/docker-entrypoint-initdb.d/10-create-roles.sql:ro`.
  - `healthcheck`: `["CMD", "pg_isready", "-h", "127.0.0.1", "-U", "app_owner", "-d", "business_software"]`, with `interval: 2s`, `timeout: 5s`, `retries: 30`.
  - A top-level named volume `pgdata`.
  - A short comment above `image` saying the integration test reads this line.

- [ ] **Step 3: `.env.example` and `.env`; root script.**
  - `.env.example` holds the four variables with placeholders (`change-me-...`). `MIGRATION_DATABASE_URL=postgresql://app_owner:change-me-owner@127.0.0.1:5432/business_software`. A comment says to use letters and digits only.
  - Copy it to `.env` and replace each placeholder with a random 32-character hex value (`-join ((1..16) | % { '{0:x2}' -f (Get-Random -Max 256) })`).
  - Root `package.json` script: `"db:up": "docker compose up -d --wait"`.

- [ ] **Step 4: Start it on an empty volume and check.** Run `pnpm db:up`. Expected: it returns after the service is `healthy`. Then:
  - `docker compose exec -e PGPASSWORD=<owner pw> db psql -h 127.0.0.1 -U app_owner -d business_software -c "select current_user"` → `app_owner` (Review Focus 2).
  - `docker compose exec db psql -U postgres -d business_software -c "select rolname, rolsuper, rolbypassrls, rolcreaterole, rolcreatedb from pg_roles where rolname like 'app_%'"` → two rows, every flag `f`.
  - `docker compose port db 5432` → `127.0.0.1:5432` (Review Focus 4).
  - `docker compose exec db psql -U postgres -tAc "show data_directory"` → `/var/lib/postgresql/18/docker`.

- [ ] **Step 5: Data survives a restart (Review Focus 1).** As `app_owner`: `create table persist_check (n int); insert into persist_check values (1);`. Run `docker compose down` (no `-v`), then `pnpm db:up`. Expected: `select n from persist_check` → `1`. Then `drop table persist_check` (a scratch table made in this step; the only `DROP` allowed without asking).

- [ ] **Step 6: Missing password (Review Focus 3).** Write a scratch env file without `APP_RUNTIME_PASSWORD` in the scratchpad, then run `docker compose --env-file <that file> config`. Expected: non-zero exit and the message `set APP_RUNTIME_PASSWORD in .env`. Delete the scratch file.

- [ ] **Step 7: Scan and commit.** `git status` must not list `.env`. Run `pnpm format:check`, which also formats `compose.yaml`.
  ```bash
  git add compose.yaml .env.example packages/db/bootstrap/create-roles.sql package.json
  git commit -m "build: run postgresql 18 in docker compose with app roles"
  ```

### Task 2: `packages/db`, the first migration, and the integration test

**Files:**
- Create: `packages/db/package.json`, `packages/db/tsconfig.json`, `packages/db/drizzle.config.ts`, `packages/db/vitest.config.ts`, `packages/db/src/schema.ts`, `packages/db/src/roles.test.ts`, `packages/db/migrations/0000_runtime_grants.sql` (+ `migrations/meta/`, generated)
- Modify: `pnpm-workspace.yaml` (catalog), `package.json` (root scripts), `.prettierignore`, `pnpm-lock.yaml`

**Interfaces:**
- Consumes: `compose.yaml` line `image: postgres:18`; `packages/db/bootstrap/create-roles.sql`; env var `MIGRATION_DATABASE_URL` (Task 1).
- Produces: package `@business-software/db` with scripts `typecheck`, `test`, `db:generate` (`drizzle-kit generate`), `db:migrate` (`drizzle-kit migrate`); migrations folder `packages/db/migrations`; root scripts `pnpm db:migrate`, `pnpm db:generate` (both `pnpm --filter @business-software/db <script>`).

- [ ] **Step 1: Scaffold the package.**
  - `package.json`: name `@business-software/db`, version `0.0.0`, private, `"type": "module"`, the scripts above, plus `"test:watch": "vitest"`. Dependencies: `drizzle-orm`, `pg`. devDependencies: `drizzle-kit`, `@types/pg`, `@types/node` (catalog), `@testcontainers/postgresql`, `typescript` and `vitest` (catalog). No `exports` yet; P0.4 adds the client.
  - `tsconfig.json`: extends the base, `"types": ["node"]`, `include: ["src", "drizzle.config.ts", "vitest.config.ts"]`.
  - `vitest.config.ts`: `testTimeout: 30_000`, `hookTimeout: 180_000` (the first run pulls the image).
  - `src/schema.ts`: one comment saying tables start in P1.1, then `export {};`.
  - Add `@types/node` (24.x) to the catalog.
  - Add `packages/db/migrations/meta/` to `.prettierignore`: drizzle-kit owns those files.
  - Run `pnpm install`.

- [ ] **Step 2: `drizzle.config.ts`.** If `../../.env` exists, load it with `process.loadEnvFile` (drizzle-kit runs from the package folder; variables that are already set win, as they will in CI). Throw `Error('MIGRATION_DATABASE_URL is not set: copy .env.example to .env')` when the variable is missing. Never fall back to another URL, so migrations never run as the runtime role. Settings: `dialect: 'postgresql'`, `schema: './src/schema.ts'`, `out: './migrations'`, `strict: true`, `verbose: true`.

- [ ] **Step 3: Generate the empty custom migration.** Run `pnpm db:generate --custom --name=runtime_grants`. Expected: an empty `migrations/0000_runtime_grants.sql` and a `migrations/meta/_journal.json`.

- [ ] **Step 4: Write the failing integration test**, `src/roles.test.ts`.
  - In `beforeAll`:
    - Read `compose.yaml` (`new URL('../../../compose.yaml', import.meta.url)`) and take the image with `/^\s*image:\s*(postgres:\S+)\s*$/m`. Throw if there's no match.
    - Start `new PostgreSqlContainer(image)` with `APP_OWNER_PASSWORD: 'owner-test'` and `APP_RUNTIME_PASSWORD: 'runtime-test'`, and copy `bootstrap/create-roles.sql` into `/docker-entrypoint-initdb.d/10-create-roles.sql`.
    - Open two `pg` Pools on `business_software` (host, port, user and password as fields, not a URL): `owner` as `app_owner`, `runtime` as `app_runtime`.
    - Run `migrate(drizzle(owner), { migrationsFolder })`.
    - As owner: `create table probe (id int generated always as identity primary key, note text)`. Creating it after the migrations is the point: it proves the default privileges cover tables that don't exist yet.
  - In `afterAll`: end both pools and stop the container.
  - Tests:

  ```ts
  it('gives neither app role superuser, BYPASSRLS, CREATEROLE or CREATEDB', /* select those flags from pg_roles where rolname in ('app_owner','app_runtime') → every value false, 2 rows */);
  it('lets the runtime role insert, read and update rows in new tables', /* insert note 'a' → update to 'b' → select returns [{ note: 'b' }] */);
  it.each([
    ['delete rows', 'delete from probe'],
    ['truncate a table', 'truncate probe'],
    ['create a table', 'create table sneaky (n int)'],
    ['drop a table', 'drop table probe'],
    ['read migration history', 'select * from drizzle.__drizzle_migrations'],
  ])('refuses to let the runtime role %s', async (_, sql) => {
    await expect(runtime.query(sql)).rejects.toMatchObject({ code: '42501' });
  });
  it('does nothing when migrations run again', /* count rows in drizzle.__drizzle_migrations, migrate again, count unchanged and equal to the number of files in migrations/ */);
  ```
  `42501` is PostgreSQL's `insufficient_privilege`. Asserting on the code, not the message, means the test can't pass because of an unrelated error, such as a typo in a table name (`42P01`).

- [ ] **Step 5: Run `pnpm --filter @business-software/db test`.** Expected FAIL: the insert/update test fails with `42501`, because the runtime role has no grants yet. The role test and the refusal tests pass already, because Task 1 built them. Confirm that this is the reason for the failure.

- [ ] **Step 6: Write `migrations/0000_runtime_grants.sql`.** Two statements, with a comment pointing to ADR 0007 rule 1:
  ```sql
  ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT, INSERT, UPDATE ON TABLES TO app_runtime;
  ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT USAGE, SELECT ON SEQUENCES TO app_runtime;
  ```
  Without `FOR ROLE`, they apply to the role that runs migrations, `app_owner`, which owns every future table.

- [ ] **Step 7: Run `pnpm check`.** Expected: PASS. All of `shared`'s 45 tests and 8 db tests.

- [ ] **Step 8: Migrate the local database.** `pnpm db:migrate` → applies `0000`. Run it again → nothing to apply. `docker compose exec db psql -U postgres -d business_software -c "\ddp"` → shows the `app_runtime=arw` default privileges for tables.

- [ ] **Step 9: Prove the test can fail (planted error).** Temporarily add `DELETE` to the tables grant in `0000`. Run the db tests → `refuses to let the runtime role delete rows` fails. Revert. (Same idea as P0.2: a check that can't fail proves nothing.) The local database already ran the correct `0000`, so it's unaffected. Don't run `db:migrate` while the planted error is in place.

- [ ] **Step 10: Scan and commit.**
  ```bash
  git add packages/db pnpm-workspace.yaml pnpm-lock.yaml package.json .prettierignore
  git commit -m "feat(db): add drizzle migrations and runtime grants without delete"
  ```
