# P1.4 Login & Sessions — Design Spec

- **Date:** 2026-11-19 (fast track Day 3, lane 3)
- **Status:** Approved. The owner gave the OK on 2026-11-19 and took the recommendation on all 11 questions in section 13.
- **Requirements:** Module 00 (DECIDED): #17 (owner's password for sensitive changes), #18 (shared counters), #20 (every action against the person logged in), #21 (owner auto-lock), #22 (several counters), #27 (owner logs in by email), #28 (staff by username; the computer remembers its business), #29 (staff idle logout), #30–#34 (email reset, recovery key, confirmation, staff resets, deactivation). Sitting 2: **D4 option A** (only the database sets `entry_log.id`/`created_at`), **06 L2** (logins, logouts, owner lock/unlock and permission changes are logged; failed logins stay with the rate limit). D1: stay free (DuckDNS, SES in its sandbox).
- **ADRs it builds on:** 0007 (data safety), 0009 (server sessions), 0027 (tenancy), 0028 (entry log), 0035 (Argon2id), 0036 (request rules).

## 1. Goal and success criteria

The owner logs in with email and password, staff with username and password on a counter the owner has logged in on, and every request after that knows who is calling, for which business and branch. Sessions lock or end on time, can be revoked at once, and nothing a visitor does can backdate history.

Done when:

1. `POST /api/login` (owner) and `POST /api/login/staff` set a session cookie; a wrong email, username or password all answer the same `401 {code:'wrong_login'}`, in about the same time.
2. `SessionResolver` is the real lookup: every non-public route works for a logged-in owner, and answers `401 not_logged_in` / `401 locked` / `401 session_ended` otherwise. No route changes (ADR 0036).
3. The owner's session locks after `owner_lock_minutes` idle; unlocking needs the password. A staff session ends after `staff_idle_minutes`. A deactivated login's sessions stop working on the next request.
4. Login, signup, reset and recovery are rate-limited; a forged `X-Forwarded-For` doesn't change the counted IP.
5. Every API answer carries `Cache-Control: no-store`.
6. Unsafe requests from a session need its CSRF token; public unsafe routes need a same-origin request.
7. Forgotten password: by recovery key always; by email link once the email is confirmed. A used recovery key stops working and a new one is shown once.
8. `app_runtime` can't insert `entry_log.id`, `business_id` or `created_at` (`42501`), and the guard test fails if it ever can.
9. Session and reset tokens, recovery keys and device tokens are stored only as hashes.
10. The guard test passes, with exactly the definer functions on `DEFINER_ALLOWED`.

## 3. Data (migration `0006`, after P1.7's `0005_items`)

All tenant tables follow ADR 0027 (`id()`, `businessId()`, `createdAt()`, `tenantPolicy`, `FORCE`, composite keys, `unique (business_id, id)` where referenced). Nothing is deleted (ADR 0007); rows end with a timestamp.

### `users` (new columns)

| Column | Type | Rule |
| --- | --- | --- |
| `username` | text, null | staff only; `^[a-z0-9._-]{3,32}$`, stored lower-case; `unique (business_id, username)`; `check (role <> 'staff' or password_hash is null or username is not null)` |
| `email_confirmed_at` | timestamptz, null | #32 |
| `password_changed_at` | timestamptz, null | set on every change |
| `deactivated_at` | timestamptz, null | #34; never deleted |

### `devices` (new tenant table): a counter computer that knows its business (#28)

`id`, `business_id`, `branch_id` (composite key; the first branch until P1.6), `token_hash` (SHA-256 hex, `unique (business_id, token_hash)`), `name` (null; "Counter 1", editable later), `registered_by` (composite key to users), `created_at`, `last_seen_at`, `revoked_at`.

### `sessions` (new tenant table)

| Column | Rule |
| --- | --- |
| `user_id`, `branch_id`, `device_id` (null) | composite keys |
| `token_hash`, `csrf_hash` | SHA-256 hex; `unique (business_id, token_hash)` |
| `created_at`, `last_active_at` | `last_active_at` written at most every 15 s |
| `locked_at` | owner only; null when unlocked |
| `ended_at`, `end_reason` | `check in ('logout','idle','replaced','password_changed','deactivated','reset')` |
| `user_agent` | first 200 characters, for "where am I logged in" |

No IP address is stored (personal data we don't need; rate limits keep IPs in memory only).

### `auth_tokens` (new tenant table): email confirmation and reset links

`id`, `business_id`, `user_id` (composite key), `kind` (`'confirm_email'` or `'reset_password'`), `token_hash`, `created_at`, `expires_at` (confirm 7 days, reset 30 minutes, question 6), `used_at`. A partial unique index keeps one open token per user and kind; making a new one marks the old one used.

### `recovery_keys`

Unchanged (P1.3). Using or replacing a key sets `used_at` and inserts the next one in the same transaction.

### `auth.owner_logins` (new, **not** a tenant table): the one cross-business read

Login by email (#27) happens before any business is known, and under `FORCE` RLS even the table owner sees no `users` rows without one. So the email → business mapping lives in its own schema:

- Schema `auth`, table `owner_logins (email text primary key, business_id uuid not null, user_id uuid not null)`, no RLS (it isn't tenant data: an email and two IDs).
- `app_runtime` has **no USAGE on schema `auth`**, so it can't read or write the table at all. `auth` joins the guard's `NOT_TENANT_SCHEMAS` list, and lane 2's new rule ("no USAGE on `NOT_TENANT_SCHEMAS`") then checks exactly what we want. Rate limits live in memory (section 7), so P1.4 needs no schema the app *can* use, which removes the clash lane 2's design noted.
- Two `SECURITY DEFINER` functions in `public`, owned by `app_owner`, each `SET search_path = pg_catalog, pg_temp`, `REVOKE EXECUTE … FROM PUBLIC`, `GRANT EXECUTE … TO app_runtime`, both on `DEFINER_ALLOWED` with their reason:
  - `app_find_owner_login(email text) returns table (business_id uuid, user_id uuid)`: one row or none. Never returns a hash.
  - `app_register_owner_login(user_id uuid)`: called inside the signup transaction. It runs with the transaction's `app.business_id`, so it can only see (and register) the current business's owner row, and it copies that row's email. It can't be used to map an email to someone else's business.
- New guard rule `definer_search_path`: every function on `DEFINER_ALLOWED` must pin `search_path` (`proconfig`). Probed with a function that doesn't.
- No backfill: the migration runs as `app_owner`, which can't read `users` under `FORCE` (ADR 0027's trap). RDS has no business rows (the live server never ran P1.3). On a local database, owners signed up before this migration can't log in by email: sign up again (the runbook says so; wiping the volume with `docker compose down -v` needs the owner's OK, rule 7).

### `entry_log` (D4, option A)

Hand-written in the migration:

```sql
REVOKE INSERT ON entry_log FROM app_runtime;
GRANT INSERT (branch_id, actor_id, action, entity_type, entity_id, reason, before, after)
  ON entry_log TO app_runtime;
```

`id`, `business_id` and `created_at` now always come from their defaults (`uuidv7()`, `app_current_business_id()`, `now()`). Drizzle names every column in an insert, so `recordEntry` writes its insert with `sql` and an explicit column list (`before`/`after` as `$n::jsonb`). Proved test-first: a Drizzle `tx.insert(entryLog)` fails with `42501`, `recordEntry` works. New guard rule `database_set_columns`: `app_runtime` has no INSERT or UPDATE on `entry_log.(id, business_id, created_at)`, via `has_column_privilege`. Dated note on ADR 0028; P1.20 (c) and the 06 flag rules already say the demo's log rows carry the seeding date.

## 4. Tokens and cookies

All tokens are 32 random bytes (base64url), stored as SHA-256 hex and compared through a unique index lookup (no timing leak to compare). The business ID travels **next to** the token, so every lookup except login-by-email is an ordinary `withBusiness` read under RLS (scan item a).

| What | Format | Where |
| --- | --- | --- |
| Session | `<businessId>.<token>` | cookie `__Host-session`: `HttpOnly; Secure; SameSite=Lax; Path=/`, no `Max-Age` (ends when Chrome closes; the server's idle rules end it anyway) |
| Device | `<businessId>.<token>` | cookie `__Host-device`: same flags, `Max-Age` 400 days (Chrome's cap), refreshed at each owner login |
| CSRF | `<token>` | returned in the login and `GET /api/session` body, kept in memory by the web app, sent as `X-CSRF-Token` |
| Reset / confirm link | `/reset/<businessId>/<token>`, `/confirm-email/<businessId>/<token>` | email; the page POSTs the token (a GET never consumes it, so mail scanners can't) |
| Recovery key | P1.3's 32 Crockford characters | typed with the email; found through `app_find_owner_login` |

A malformed cookie (no dot, not a UUID) is "no session", never a 500. Local development runs over plain HTTP: `__Host-` needs `Secure`, so the cookie names and the `Secure` flag come from config (`COOKIE_SECURE`, `false` only in `.env` for `pnpm dev`). *To check while building:* whether Chrome accepts `Secure` cookies on `http://127.0.0.1`; if it does, dev uses the same names.

## 5. Login, sessions, lock

### Routes

| Route | Guard | What it does |
| --- | --- | --- |
| `POST /api/login` `{email, password}` | `@Public()`, same-origin, rate-limited | `app_find_owner_login` → `withBusiness` → verify → new session (+ device cookie) |
| `POST /api/login/staff` `{username, password}` | `@Public()`, needs a live device cookie | `withBusiness(device's business)` → verify → session on the device's branch |
| `GET /api/session` | `@Permission('session.own')` (everyone has it) | who am I, business, branch, role, lock state, CSRF token, `emailConfirmed` |
| `POST /api/session/lock` | `session.own` | owner's "Lock now" |
| `POST /api/session/unlock` `{password}` | allowed on a **locked** session only | clears `locked_at` |
| `POST /api/logout` | `session.own` | ends the session (`logout`) |

The permission guard needs one addition: a locked session resolves to a caller marked `locked`, and every route except unlock, logout and `GET /api/session` answers `401 {code:'locked'}`.

### Rules

- **Unknown email or username:** a dummy Argon2id verify runs, so the answer takes about as long as a wrong password. Same code `wrong_login` for both.
- **Deactivated user:** `wrong_login` too (no hint the login exists).
- **Rehash at login** when the stored PHC parameters are older than today's (ADR 0035).
- **One session per browser:** logging in while the cookie holds another live session ends that one (`replaced`). This is how "Switch user" works on a shared counter (#18).
- **Owner lock (#21):** when `now − last_active_at > owner_lock_minutes`, the next request sets `locked_at` and answers `locked`. The web app also runs a timer and covers the screen at the same moment, so owner data disappears even if no request is made. Unlock returns to the same page with its state (a held bill stays).
- **Staff idle (#29):** past `staff_idle_minutes`, the session ends (`idle`); the next request answers `session_ended`.
- **What counts as activity:** any request with a session, except routes marked `@Passive()` (polling such as the future alerts bell), so a background poll can't keep a session alive. The health badge needs no session.
- **Changed while building (2026-11-19):** typing a long bill makes no request, so the server would lock the owner while they type. The web app counts key presses, clicks, scrolls and touches, and sends `POST /api/session/active` (`session.own`, 204) at most every 30 seconds while there are some. `GET /api/session` is `@Public()` and passive rather than `session.own`: with no session it answers `{state: 'none', device}` so the login page knows whether to show the staff tab. Both are in ADR 0038.
- **Deactivation (#34):** the resolver joins `users` and treats `deactivated_at` as ended; deactivating also ends open sessions in the same transaction (`deactivated`).
- **Password change** (own, needs the current password): ends the user's other sessions (`password_changed`).
- **Caller** gains `sessionId`, `branchId`, `role` and `locked`. Permissions: the owner holds all; staff hold `session.own` only until P1.5.

### Entry log (06 L2)

New `ENTRY_ACTIONS`, none needing a reason: `user.logged_in`, `user.logged_out` (`after.cause`: `logout`, `idle`, `replaced`), `session.locked` (`after.idleSince`; written when the lock is noticed), `session.unlocked`, `user.password_changed`, `user.password_reset` (`after.via`: `email` or `recovery_key`), `recovery_key.replaced`, `user.email_confirmed`, `user.deactivated`, `user.reactivated`, `device.registered`, `device.revoked`. Failed logins aren't logged (L2).

## 6. Re-authentication and owner-password checks (#17)

Sensitive routes take the owner's password **in the body** (`ownerPassword`), checked by one helper, `requireOwnerPassword(businessId, password)`, which is rate-limited like login. It works for the owner re-confirming and for a staff screen where the owner types the password to approve something (Module 02 #12's discount override uses the same helper later). Stateless: no "re-authenticated until" window to get wrong. In P1.4 it guards: set a staff password, deactivate/reactivate, make a new recovery key, forget a device. P1.5 adds permission changes.

## 7. Rate limits and the proxy

- **In memory, in the API process** (one API container, ADR 0011): fixed windows, keyed per IP and per login. Nothing is written to the database for a failed attempt. A restart clears the counters; deploys are rare and manual, so that's acceptable. A second API instance would need them in PostgreSQL (noted in the ADR). This keeps the database free of non-tenant writable tables.
- Limits (question 5): login 30 per IP and 10 failures per login per 15 minutes; signup 5 per IP per hour; reset requests and recovery-key attempts 5 per IP and per email per hour; owner-password checks 10 per session per 15 minutes. Over the limit: `429 {code:'too_many_attempts', retryAt}`.
- **Argon2 memory guard:** at most 2 hashes at once (19 MiB each); up to 20 wait; beyond that `503 busy`. Caps memory on the 2 GB server (ADR 0035's consequence).
- **`trust proxy` = 1** (Caddy only; scan item c). Caddy replaces `X-Forwarded-For` from clients it doesn't trust, and Express takes the last hop. Tests: (1) unit: a forged `X-Forwarded-For` doesn't change `req.ip` beyond the one trusted hop; (2) CI `smoke`: 31 logins through Caddy, each with a different forged header, and the 31st still gets `429`.
- **`Cache-Control: no-store`** on every API answer (scan item d), set by one middleware, checked by a test that walks every route in the census.

## 8. CSRF

ADR 0009 asks for a CSRF token on unsafe requests. Every unsafe request with a session must carry `X-CSRF-Token` matching the session's `csrf_hash`, or `403 {code:'csrf'}`. Public unsafe routes (signup, login, reset, recovery) have no session, so they require `Sec-Fetch-Site: same-origin` (or a matching `Origin`), which stops login CSRF; Chrome sends both. A cross-site page can't read `GET /api/session`'s token: same origin, no CORS.

## 9. Email (new ADR)

- **`Mailer` interface** with three implementations: `SesMailer` (AWS SDK v3 `SendEmail`, credentials from the server's instance role, so no keys anywhere), `SmtpMailer` to **Mailpit** (a container in `compose.yaml`, web UI on `127.0.0.1:8025`, for `pnpm dev` and real-app checks), and `FakeMailer` in tests. Chosen by config (`MAIL_TRANSPORT`).
- **Sent from the API right after the transaction commits**, best effort: a failed send is logged (message only, never the link) and the user can press "Send again". When P2.7's outbox exists, sending moves to the worker; the interface doesn't change.
- **The demo (D1, SES sandbox):** SES sends only to verified addresses. The sender is the owner's verified address (in SSM / git-ignored `terraform.tfvars`, never in the repo). In the demo, confirmation and reset emails reach only verified addresses; for anyone else the banner says email is limited in the demo and the recovery key is the way back in (question 10). SES costs nothing at this volume (*check the current SES price with the Pricing API while building*).
- **Terraform:** an SES email identity and `ses:SendEmail` on the instance role, limited to that identity. It goes in a small follow-up PR after lane 1 (stage 7) merges, because both change `infra/terraform/demo/`. `terraform plan` and its cost come to the owner first.
- *Unverified, check while building:* a gmail.com sender through SES may fail DMARC alignment at some receivers and land in spam. A DuckDNS subdomain can't hold DKIM records, so a real domain is the only full fix (D1 says not now).

## 10. Confirmation, reset and recovery

| Route | What it does |
| --- | --- |
| `POST /api/email/confirm/send` (`session.own`, owner) | new `confirm_email` token, email the link |
| `POST /api/email/confirm` `{businessId, token}` (`@Public()`) | sets `email_confirmed_at`; logs `user.email_confirmed` |
| `POST /api/password-reset/request` `{email}` (`@Public()`) | always `202`; sends a link only to a confirmed owner email (#30) |
| `POST /api/password-reset/complete` `{businessId, token, newPassword}` (`@Public()`) | new password, token used, all the user's sessions end (`reset`) |
| `POST /api/recovery/reset` `{email, recoveryKey, newPassword}` (`@Public()`) | key checked, marked used, new key made; new password; sessions end; answers the new key once (#31) |
| `POST /api/recovery-key` `{ownerPassword}` (owner) | marks the current key used, answers a new one once (covers P1.3's "lost 201") |

Signup now also logs the owner in (question 1), registers the counter, calls `app_register_owner_login`, and sends the confirmation email after commit. The banner (#32) shows until `emailConfirmed`.

## 11. Web

- **Login page** (`/login`): email + password; a "Staff login" tab (username + password) shown only when the computer has a device cookie (`GET /api/session` says `deviceBusinessName`). Links: "Forgot password" (email or recovery key), "Create a business" (signup).
- **Lock screen:** covers the app (an inert overlay plus `inert` on the page), shows the business name, a password box and "Switch user". Owner's "Lock now" button in the top bar, plus a shortcut (`Alt+L`, through `useShortcut`, ADR 0026).
- **Route protection:** the `_app` layout loads `GET /api/session` with TanStack Query; `not_logged_in`/`session_ended` → `/login`; `locked` → lock screen.
- **Pages:** forgot password (choose email or recovery key), reset (from the link), confirm email (from the link), new recovery key shown once (reuses P1.3's screen), change password and "This computer" (name, forget) on Settings.
- Every string in `en`, `hi`, `hi-Latn`; light and dark; 1024 px; no CSP violations.

## 13. Questions for the owner

Module 00 is DECIDED; these fill gaps it doesn't cover. Each has a recommendation.

**Owner's answers, 2026-11-19:** all 11 as recommended. The ones that add to Module 00 are written there as #37–#46, with a Change log line "2026-11-19 — P1.4 design answers"; no decided point changed meaning. Question 7 is a planning choice and stays here.

1. **After signup, is the owner logged in straight away?** *Recommended: yes*, and that computer becomes the business's counter (staff can log in on it).
2. **The lock screen:** *Recommended:* a password box and a "Switch user" button; unlocking returns to the same page with nothing lost; a staff login on a locked computer ends the owner's session. Plus a "Lock now" button and `Alt+L`.
3. **Logged in on several counters at once:** *Recommended: allowed* for the owner and for staff (#22 has several counters billing together); each computer has its own session.
4. **Closing Chrome logs you out:** *Recommended: yes* (the session cookie ends with the browser); the computer still remembers its business, so staff only type username and password again.
5. **Failed-login limits:** *Recommended:* 10 wrong passwords for one login in 15 minutes → that login waits 15 minutes ("Try again at 14:35"); 30 attempts per computer in 15 minutes. The owner can always get in with the recovery key, which has its own limit. (A staff member could block the owner's login for 15 minutes by typing wrong passwords; the recovery key and the short wait are the answer.)
6. **Link lifetimes:** *Recommended:* password reset link 30 minutes, email confirmation link 7 days; each works once.
7. **Staff password reset and deactivation (#33, #34):** *Recommended:* P1.4 builds the rules and API (sessions end at once, nothing deleted); the buttons arrive with P1.5's staff page, where staff are created.
8. **Staff usernames:** *Recommended:* 3–32 characters, letters, digits, dot, dash, underscore; not case-sensitive (`Ramesh` = `ramesh`); unique within the business only.
9. **Remembered computers:** *Recommended:* remembered for 400 days (Chrome's longest), renewed at each owner login; Settings lists them ("Counter 1, last used today") with a Forget button (needs the owner's password).
10. **Email in the demo (D1):** *Recommended:* confirmation and reset emails go out only to verified addresses (yours); other visitors see "Email is limited in this demo: use your recovery key", and the recovery key is the documented way back in.
11. **Changing your own password** in Settings (current password required; logs you out everywhere else): *Recommended: yes*, though Module 00 doesn't list it. Changing the owner's **email** stays out of v1 (it needs re-confirmation and a change to the login mapping).
